# with-secrets reference

The detailed behaviour of every part, with the exact rules and limits. For what the tool is and how to start, read the [README](../README.md); for installing, enrolling machines, backup and recovery, read [operations](operations.md); for the design and threat model, read [architecture](architecture.md); for writing safe agent commands, read [agent usage](agent-usage.md).

## How approval works

1. The agent runs the command. The program checks the names against the store in `with-secrets.db` (and checks every stored ciphertext against its signed hash) and decrypts nothing.
2. It prints a **one-use link** to the terminal (stderr). The agent shows the link to you.
3. You open the link on any device that can reach it. The page shows the whole request: the program and the script as **full paths** (no `./`, no `..`), the secret names, the folder, and the agent's reason. The full path is also what runs. For the allowed forms the page shows the full command and the files it reads as code; the limits below remain. If the program or script is a symbolic link, the page adds a `Link:` line that shows where it leads. The page also shows what will run: an `Inline code:` block for code written in the command (`sh -c`, `cmd /c`, `pwsh -Command`, `python -c`, `node -e`, `perl -e`, `ruby -e`), and for every file that will be read as code (the script argument, and the program itself when it is a text file such as `evil.cmd`) its `Script file:` path, `Script SHA-256:` and a `Script contents:` block (first 200 lines, at most 16 KB; a binary or non-UTF-8 file says so). Every line of that code starts with `  | `, so no line of the agent's text can look like a line of the page (`Request id:`, `Run:`); control, bidi and zero-width characters are replaced by a mark; and these blocks are part of the text the passkey signs. A script that cannot be read, or is larger than 1 MB, refuses the run. The child gets no standard input (it reads end of file), and these variables are removed from its environment: `NODE_OPTIONS`, `BASH_ENV`, `ENV`, `PYTHONPATH`, `PYTHONSTARTUP`, `PYTHONHOME`, `PYTHONINSPECT`, `PERL5OPT`, `PERL5LIB`, `RUBYOPT`, `RUBYLIB`, `DOTNET_STARTUP_HOOKS`, `JAVA_TOOL_OPTIONS`, `_JAVA_OPTIONS`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `DYLD_INSERT_LIBRARIES`, `PERLLIB`, `ZDOTDIR`, `PYTHONUSERBASE`, `PYTHONWARNINGS`, `NODE_PATH`, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_EXEC_PATH`, `GIT_SSH_COMMAND`, `GIT_ASKPASS`, `SHELLOPTS`, `BASHOPTS`, `PS4`, `PS0`, `PROMPT_COMMAND`, and every name starting with `BASH_FUNC_`.
4. You read all of it, then press **Approve once** (or Ctrl+Enter, Cmd+Enter on a Mac). The approve controls stay off for a moment so they cannot be pressed by accident. Enter on the focused Deny button denies.
5. You prove it with a **passkey**. The passkey signs the request and the time you chose, so nothing can change the time afterwards. The program checks the proof itself, and accepts only a time the page offered. The page cannot approve anything alone. Sign-in lists all your passkeys for `localhost` (it does not name them), so it works with a password manager; new passkeys are created as discoverable keys.

If a passkey prompt closes without an answer, select **Cancel** on the page to abandon the attempt, then try the passkey action again.
6. If the proof is good, the program decrypts **only the named secrets**, passes them to the program as environment variables, and redacts them from the output. Give a comma-separated list (`--secrets DB_URL,API_KEY`) to inject several secrets in one run, or declare them in the project's `.env` (see [Project `.env` declarations](#project-env-declarations)). There is no `--all`: every name must be written out.
7. It writes an audit line (names, command, result, and a hash of any script file in the command; never values).

Deny, a wrong proof, an error, or no answer before the time limit all deny the run (exit code 3); a run blocked on approval says which in its own sentence: "The user did not approve (denied on the page)" for Deny, "Nobody answered before the approval time limit" for a timeout (nothing ran; ask again), and the signed audit event records `user-denied` or `approval-timeout`. The link works once. A run needs the host service (exit code 6 when it is not running, exit code 7 when what answers is not this machine's service or no identity is pinned yet, exit code 8 when the authority is locked; see [The host service](#the-host-service) and [The authority lock and the admin web app](#the-authority-lock-and-the-admin-web-app)).

### Pending run requests

The authority's **Access** page lists pending run requests under **Waiting for you**, with the first expiry at the top. Select the command to review the reason and what will run. The authority holds up to 64 pending requests in memory. The run's deadline is the earlier of its request expiry and the configured approval timeout, which defaults to five minutes.

Preparing a passkey proof reserves one active challenge for the browser session that requested it. That session can reuse its challenge for up to five minutes, capped by the run's deadline. Other sessions cannot replace it while it is active. A session can prepare another challenge after it expires if the run is still pending. Full review details remain in memory for ten minutes after a decision.

## First-time setup

Run `with-secrets admin` in **your own terminal** to open Quick Start on an unconfigured installation. It starts the local service locked and prints the device fingerprint. Enter the code shown on the page in that terminal, then compare the full fingerprint on both screens.

Create a PRF-capable admin passkey. A second explicit gesture signs the initial store and the verified setup context and releases the keys for the initial unlock. The service trusts the local machine, pins the authority key, and signs in the setup browser. Save the recovery code offline. The finish screen has an optional example of how a command requests a secret. Select **Open with-secrets** to go to Overview.

## The authority lock and the admin web app

**The authority starts locked.** An admin passkey with PRF must unlock it after each start. The service keeps the store and Review keys in memory until lock or shutdown and clears pending launches and sessions on lock. Existing grants retain their scope and expiration and can cover runs after the next unlock. A paired host reconnects after restart without a local unlock. It can get secrets only while the authority is unlocked, reachable and vouches for that host.

**There are no lock, unlock or other `admin` verbs.** `with-secrets admin` with nothing after it (only `--port N`, the admin web app's port, and `--debug` are accepted) checks that the program on the command line's channel is this machine's host service (the same identity check as a run), prints the link of the authority's **admin web app** (`https://with-secrets.localhost:PORT/admin`, loopback only) and whether the service is running and locked, and, in a terminal on Windows, opens the link in your browser. It changes nothing and needs no passkey. Every administration function lives in the app.

### The admin web app

The administration is a **JSON API** on the service's own loopback port under `/api/v1` and the **administration web app** (React and TypeScript) uses it: the app is embedded in the exe and served at `/admin` on the same origin (any application route under `/admin` gets the app; a missing file or anything under `/api` never does). There is no server-rendered page. Metadata views are available from the local UI without sign-in. Administration starts with a verified passkey and high-impact changes have their own passkey confirmation. Without the app built into the exe, `/admin` answers the JSON 404 `web-application-not-built`. The API is described by an OpenAPI 3.1 document served at `/api/v1/openapi.json` (a copy is in `docs/api/openapi.json`; a test fails if they differ). Every answer carries `X-Api-Version: 1`; a request with another `X-Api-Version` is refused with a problem document listing the supported versions. Errors are RFC 9457 `application/problem+json` (a stable `code`, no secret, path or internals). Request bodies are small JSON (at most 4 KiB, validated against the schema, unknown or duplicate members refused). There is no CORS. Every machine function that used to be an `admin` verb is here:

- **Status** (`GET /api/v1/status`, public): running, locked or unlocked (and how), the **unlock mode**. `POST /api/v1/session` starts a sign-in; while locked, **unlock** is an operation.
- **Machines** (`/api/v1/machines`): fingerprint, status, security revision, host name and friendly name. Operations: `machine-approve` (with a friendly name; it pins the authority key for this machine), `machine-disable`, `machine-enable`, `machine-untrust`, `machine-trust` (the **full** 64-digit fingerprint is the confirmation), `machine-rename`, `machine-host-change`, and re-pin of the authority key.
- **Grants** (`/api/v1/grants`): list, `grant-extend`, `grant-renew`, `grant-replace`, `grant-revoke` (see [Grants](#grants)).
- **Audit** (`/api/v1/audit/events`, `/audit/changes`, `/audit/gaps`): host events, **numbering gaps**, and authority changes. Search by text and time range, open **More filters** for additional criteria, and select a row for its details (see [Audit trail of the host service](#audit-trail-of-the-host-service)).
- **Settings** (`/api/v1/settings`): the audit retention, the admin **session timeouts**, and `authority-key-rotate` and `authority-key-recover`.
- **Passkeys** (`/api/v1/passkeys`): `passkey-enroll` and `passkey-unenroll`.

**Browsing.** Anyone who can reach the local Admin port can see metadata such as secret names, machines, grants, passkey names, provider and mount names, settings, and audit activity. The public audit views omit arguments, free-form detail, and attached metadata. Provider configuration, full grant review text, and pending approval details require sign-in. Secret values are never shown.

**Signing in.** An admin passkey starts an admin session. An approval passkey can sign in to approve runs, manage grants, and submit signed secret batches. Choose **Unlock and sign in** to unlock a locked authority with PRF and establish an admin session with the same tap. The browser claims the session with `POST /api/v1/session/claim` and gets an HttpOnly, SameSite=Strict cookie and a separate secret for the `X-Admin-Token` header. Protected requests require the cookie and header together. Changes also require the local Admin origin.

**Editing lock.** In Settings, **Lock editing after inactivity** defaults to 15 minutes. Set it to 0 for **Never**, or choose 1 to 120 minutes. Changes and deliberate interactions with the Admin page count as activity. Background polling does not. When editing locks, you can keep browsing and choose **Resume editing** or **Sign out**. An admin passkey or an enrolled authenticator app can resume the existing session. The session keeps its original admin identity. **Lock editing** locks the current browser session immediately.

**Access credentials.** From **Access credentials**, choose **Add authenticator app** and confirm with an admin passkey. In Google Authenticator or a compatible app, create a time-based account using the setup key shown in Admin. The setup key is shown once. You can add several apps and remove each one individually with an admin passkey. Choose **Resume editing** and enter the current six-digit code. Accepted codes are single-use and attempts are rate-limited. Rotating the secret-store key clears the enrolled authenticator apps.

**Session end.** The absolute timeout defaults to eight hours and accepts 1 to 1440 minutes. Sign-out, authority lock, and service restart also end the session. After it ends, a fresh admin tap is required to start another admin session. The authority keeps up to eight signed-in browser sessions and evicts the least recently active when full.

| Action | Required credential or session |
| --- | --- |
| Browse metadata | None on the local Admin port |
| Open an admin session or unlock the authority | Admin passkey, with PRF for authority unlock |
| Resume a locked admin session | Admin passkey or enrolled authenticator app code |
| Lock editing, revoke a grant or pending pairing invitation, or lock the authority from Admin | Active admin session |
| Approve a run, extend or renew a grant, allow repeat runs, or submit up to 20 secret values | Fresh eligible enrolled passkey tap |
| Change machine trust, passkeys, provider configuration, mounts, or protected settings, move or remove secrets, or rotate or recover keys | Fresh admin passkey tap |

**API.** The Admin UI sends a routine change to `POST /api/v1/authorizations/inline` with `applyFromSession: true` after confirmation. Only an active admin session can use that option on an operation that supports it. A protected operation returns a one-use challenge bound to its operation and parameters. The service applies the change when it verifies the assertion and retains the outcome at `GET /api/v1/authorizations/{id}` for that same browser session. Auditing records the signer or the admin identity of the session that applied the change.

While the authority is unlocked, the service holds the decryption keys in memory and enforces approval in software. A process that can read the service's memory can obtain the keys, and a defect in the approval check could release a secret. A convenience key can approve any request while unlocked, including a grant with no end.

**Limits.** Locking is a gate in the service process, not a second layer of encryption: the authority signing key stays protected by the operating system and the lock decides when this process asks it to be used. Cookies are not isolated by port on `localhost`, so another program served on `localhost` in the same browser profile is sent the session cookie; a protected request also needs the session secret and changes require the local Admin origin. A local program can start a sign-in or an operation and ask you to tap: read the page text before you tap (it names the operation and says what it changes) and tap only for what you just chose. Adding or removing a passkey uses the existing enrollment pages (the new passkey's code is typed in the terminal that runs the service). The exit code **8** ("the authority is locked") can also be a child program's own exit code: the tool means "locked" only when it printed its one `with-secrets: the authority is locked ...` line on stderr (a locked authority never starts the child), so check that line, not the number alone. Zeroing is best effort (the runtime may have copied memory). The lock does not stop a program that already started. Malware running as your user can still read the user's files, drive your browser or wait for you to tap.

## Machine identity and the admin app


The host service has a **machine identity**: an ECDSA P-256 key made on first start (`with-secrets service`) and kept by Windows CNG as a non-exportable key, in the Platform Crypto Provider (TPM) when there is one and otherwise silently in the software provider. **On Linux (and WSL) the key is a file, not a CNG key**: ECDSA P-256 in `~/.with-secrets/keys/` (mode 0600, directory 0700). Before using it the program refuses, with one line that names the path and the fix (exit code 4): a link in place of the file or folder, a file or folder of another owner, a file group or other can access, a folder group or other can enter, or any folder up to the store folder that group or other can write (a sticky-bit folder is accepted); a new key is created exclusively and atomically; the service and `pair` are made non-dumpable and the key bytes and PRF output are `mlock`ed best effort (a refusal is one warning line in the log). That is **weaker than Windows CNG**: the file is an ordinary file, so anything running as that user (or root) can copy it, and a copy is the whole machine identity; there is no TPM, keyring or secret-service support. A container is a separate machine with its own identity and needs a persistent volume for `~/.with-secrets/keys`; see [docs/operations.md](operations.md) section 8 ("Linux host hardening": a dedicated service user or container, the key volume mounted only in the service container, the key folder out of backups). **Copied-identity warning:** when an authority sees a machine's connection replaced from a different address 3 times within 10 minutes (fixed), it writes a signed audit event and the Machines screen shows "This machine's identity may have been copied", with "Disable this machine if you did not start both."; nothing is disabled for you. Its **fingerprint** is the SHA-256 of the public key (shown as 16 groups of 4 hex digits). The service prints only the fingerprint and the host name. A separate **authority signing key** signs the authority's answers; its public key is pinned in `host.json` in the store folder (public data only) when this machine is first approved, and the host rejects an answer signed by any other key. Machine records share `with-secrets.db` with the secret store, provider data and audit history.

**Local machine trust.** Quick Start shows the full device fingerprint in the terminal and browser. The final setup confirmation trusts that device and pins the authority key in `host.json`. An already configured installation with a pending local machine can still verify and approve it in **Machines**. A run first asks the service to prove the identity pinned in `host.json`. A missing or mismatched identity stops the run before anything is sent.

| Machine action (button) | What it does |
| --- | --- |
| **Approve** | Pending to Trusted, with a friendly name; pins the authority key for this machine |
| **Disable** / **Enable** | Trusted to Disabled (the revision goes up, grants end) / Disabled to Trusted (starts clean) |
| **Untrust** / **Trust again** | Withdraw trust (revision up) / trust again; **Trust again** needs the **full** 64-digit fingerprint typed as the confirmation |
| **Rename** | Change the friendly name (display only; revision unchanged) |
| **Approve host name change** | Accept the host name a Trusted machine started using; until then it is denied and the change is recorded |

Each change needs its own one-use page and an admin passkey tap; the page text, which the passkey signs, names the action, the machine's full fingerprint, host name, status and security revision, so a tap cannot be reused for another change. A non-admin key, no answer, a machine that changed meanwhile (the revision, or the host name that was shown) or a locked authority changes nothing. Only a **Trusted** machine is ever shown an approval or decrypts anything; Pending, Disabled and Untrusted machines are denied, nobody is asked, and nothing is decrypted.

**Authority key rotation and recovery.** A routine rotation is a signed transition (the new key signed by the current one); the host follows it by itself and moves its pin. If the authority key is lost or not trusted there is no transition: recovery is an explicit administrator action (**Recover** in the app's **Settings**) that makes a new key and pins it for this machine; other hosts must be enrolled again. **Rotate** is the routine rotation. Both need an admin passkey tap like every other change, and are refused while the authority is locked. A grant is honoured only under the machine's current security revision and never across a service restart. Limits: `host.json` can be written by any process of the same user, so this is no protection against a hostile same-user process; the CLI's identity check is not bound to the connection, so a relaying impostor on the port could still read the request it relays; CNG exists on Windows only, so `service` refuses elsewhere.

## Providers and mounts

Open **Providers** in the local authority’s administration app. The list shows each provider's type, health, and mount count. Select a provider to open its configuration and mounts. Choose the provider type when you add an instance. The form shows the settings for that type, and the type is fixed on subsequent edits. Use the API to configure a registered adapter that has no form in the app. Confirmed changes appear in a banner on the page. Removing a provider returns you to the provider list.

A tree mount maps a logical folder to a provider path. A single-secret mount maps one logical secret name to one provider path. **Secrets** shows manually added and mounted secrets in one tree. A name such as `apps/API_KEY` appears under **apps**, and names without a folder appear at the root. Use **Mount provider** at the top of **Secrets** to choose a configured provider and enter a path. The path field suggests existing folders. Mounted provider names are read-only in this view. Leave the provider path empty on a tree mount to list the provider root.

Use the pencil beside a manually added secret to change its name or folder. Leave **New value** blank to keep the stored value. Enter a new value to replace it in the same passkey-confirmed save.

The provider API accepts configuration as a JSON object of at most 2,000 characters after formatting whitespace is removed. Use non-secret settings such as URLs and vault identifiers. For providers with a dedicated token field, the app sends the token to the authority to seal before requesting passkey approval. The service rejects configuration keys that look like credentials, including names containing `token`, `password`, or `credential`. Max staleness is measured in whole seconds up to 24 hours. Zero selects live retrieval. A positive duration enables encrypted caching on the authority and bounded fallback during provider outages.

For **Bitwarden Secrets Manager**, install `bws` on the authority service’s PATH. In **Providers → Add provider**, choose **Bitwarden Secrets Manager**, enter the machine-account access token, and enter the HTTPS server URL for that token. WithSecrets encrypts the token in the provider configuration and binds it to that server. It passes the token to the isolated `bws` process for each request. The service’s environment needs no token for providers configured this way.

Use **Change configuration** to edit the connection and cache freshness together. Enter a replacement token when you change the server. Leaving the token field blank keeps the current credential for its existing server. An admin passkey confirms the changes together. In **Add mount**, pick **Entire project** or **Single secret** and choose a Bitwarden project by name. For a single-secret mount, also choose the secret by name. Enter the path you want to use in WithSecrets. WithSecrets uses a temporary Bitwarden profile that disables persistent CLI authentication state.

For **LastPass**, add a provider with the account email and region. The app uses a one-hour refresh lifetime for new LastPass providers. Add a single mount for each field using its numeric LastPass item ID. On that provider's page, choose **Refresh values** from an interactive desktop on the authority machine. Compare the four-character code, requester, full account email, and mounted fields in the browser and the WithSecrets terminal. Enter the master password in the terminal and return to the browser to approve saving the encrypted values with your WithSecrets passkey.

A refresh requires a positive cache freshness window and 1 to 100 individually mounted fields. Only one refresh can run per provider instance. The initiating browser session owns the flow, and the operator has four minutes from its start to approve the staged values. If the provider or its mounts change before approval, start a fresh refresh. Locking the authority or signing out of the initiating session discards the pending refresh.

The terminal refresh supports personal login fields. Shared folders, protected items and sign-ins that require additional LastPass verification are unsupported. WithSecrets streams the vault without writing it to disk, keeps only the approved fields in its encrypted cache, and asks for another refresh after the configured lifetime. The desktop launcher uses a Windows console, Terminal on macOS, or GNOME Terminal, Konsole, or xterm on Linux.

When configuring a LastPass mount through the API, use the numeric item ID followed by the field path suffix.

| Field | Path suffix |
| --- | --- |
| Password | `/F_70617373776F7264` |
| Username | `/F_757365726E616D65` |
| URL | `/F_75726C` |
| Note | `/F_6E6F7465` |

The six operations below require a fresh, operation-bound administrator passkey tap. Adding or removing a mount ends the active grants for names that change source. The passkey review shows how many grants will end. A provider instance can be removed after its mounts have been removed.

| Operation | API route | Audit outcome |
| --- | --- | --- |
| `provider-add` | `POST /api/v1/providers` | `provider-added` |
| `provider-config` | `PUT /api/v1/providers/{id}/config` | `provider-config-changed` |
| `provider-max-stale` | `PUT /api/v1/providers/{id}/max-stale` | `provider-max-stale-changed` |
| `provider-remove` | `DELETE /api/v1/providers/{id}` | `provider-removed` |
| `mount-add` | `POST /api/v1/mounts` | `mount-added` |
| `mount-remove` | `DELETE /api/v1/mounts/{id}` | `mount-removed` |

The page prepares each tap through `POST /api/v1/authorizations/inline`. It checks proposed configurations and mount paths through `POST /api/v1/providers/validate`. Validation errors block the change and warnings require confirmation. The authority retries validation at the tap and refreshes the affected mounts after a successful mount addition or configuration update.

`GET /api/v1/status` advertises the capability as `capabilities.providers`. Read routes list provider types, instances, mounts and namespace entries. Entry responses carry metadata only. `POST /api/v1/mounts/{id}/refresh` requires an administrator session with `admin.decide` and records `namespace-refreshed` without a passkey tap. The authority also attempts reconciliation every 15 minutes per mount while unlocked and the adapter is ready. See the [OpenAPI contract](api/openapi.json).

## Secret names

A secret name is `NAME` or `folder/NAME`: one to four segments separated by a single `/`, at most 200 characters in all. The last segment is the name proper: letters, digits and underscores, starting with a letter, **in any case** (`STRIPE_KEY`, `stripe_key` and `Stripe_Key` are three different secrets), and not starting with `DOTENV_` (except `DOTENV_PRIVATE_KEY...`, a reserved Dotenvx credential name; see [Dotenvx encrypted values](#project-env-declarations)). Each folder segment is 1 to 64 of letters, digits, `_`, `.` and `-`, and is not `.` or `..`. So `STRIPE_KEY`, `team/STRIPE_KEY` and `team/payments/STRIPE_KEY` are names; `team//KEY`, `/KEY`, `KEY/`, `../KEY`, `a b/KEY`, `a?/KEY`, `a#/KEY`, `a%41/KEY`, `a\KEY`, `1KEY` and five or more segments are refused. The whole path is the store name, and it is data only: it is never a file path, and it is compared exactly (case counts, so `Team/KEY` and `team/KEY` are two secrets; the approval page shows the exact name). The Secrets page warns when a name differs from a stored name, or from another name of the same request, only by case, or only by look-alike characters (`l`, `I`, `1` and `O`, `0`); `--needs` adds `; differs only by case from: X` or `; looks like: X`. It is a warning, never a refusal. One rule is used everywhere: the Secrets page, the audit filters, `--needs`, `.env` references and the store. A folder has no meaning to the program; it only groups names (the Secrets page shows the whole path).

An environment variable cannot hold a `/`, so `--secrets` takes plain names only (the variable has the secret's name). A secret in a folder reaches a program through a `.env` reference: `STRIPE_KEY=secret://team/payments/STRIPE_KEY`.

## Project `.env` declarations

A project declares what it needs in its `.env` instead of the agent listing names. Example:

```
# .env in the project folder
LOG_LEVEL=Debug
STRIPE_KEY=secret://team/payments/STRIPE_PRODUCTION_KEY
GITHUB_TOKEN=secret://GITHUB_TOKEN
```

```
with-secrets --needs                                  # what would be asked for (names only)
with-secrets --reason "deploy" -- ./deploy.sh         # --secrets is no longer needed
with-secrets --secrets DB_URL --reason "deploy" -f .env -f ../shared.env -- ./deploy.sh
```

- **Files.** The default is `.env` in the working directory (no search upward). `-f`/`--env-file PATH` (repeatable) replaces that list. A missing default `.env` means no declarations; a missing `-f` file is an error (exit 2). A file over 1 MB is refused, and it must be a regular file (it is opened once and read to the cap); parsing stops at the first variable over 400 in one file. Limits, all errors (exit 2) and never cut: at most 16 files, 200 ordinary variables (encrypted ones count) and 200 pairs; a variable name of at most 128 characters; an ordinary value of at most 4096 characters. A `-f` file outside the working directory, or a symlink/junction, gets a `Link:` line on the page. The files are read once, when the request is built: the approval page, the fingerprint, the audit row and the launch all use that one reading, so a `.env` changed while the page is open changes nothing.
- **Syntax (Dotenvx style).** `NAME=value`, `#` comment lines, an optional `export `, blank lines, and values with single quotes (literal), double quotes (`\n`, `\r`, `\t`, `\"` and `\\` are escapes) or none (a ` #` ends the value). No `${}` expansion and no multiline values yet. A name is letters, digits and `_`, not starting with a digit. A bad line is an error that names the file and line (never the value). A name repeated in one file: the last line wins.
- **Three kinds of value, decided on the final value of each name.** `secret://...` is a reference; a value starting with `encrypted:` is a Dotenvx encrypted value (see **Dotenvx encrypted values** below; one that is overridden is ignored and asks for no key); anything else is an ordinary value.
- **Composition (like Dotenvx).** The first file wins per name. An existing environment variable beats an ordinary `.env` value (the program simply inherits it). A `secret://` reference always beats an inherited variable of the same name: it is explicit. A reference that loses to an earlier file's value is never requested, so only the final references reach the approval page and the store. `--secrets NAME` is a pair `NAME <- secret NAME`; the same variable given by `--secrets` and by a different reference is an error, and `--secrets` beats an ordinary `.env` value of that name.
- **Reference grammar.** `secret://NAME` or `secret://folder/NAME` (the rules of [Secret names](#secret-names)). The whole path is the store name: `secret://team/payments/STRIPE_KEY` is the secret `team/payments/STRIPE_KEY`. The left side is the variable the program receives, and may differ from the secret: `STRIPE_KEY=secret://team/payments/STRIPE_PRODUCTION_KEY`. Anything else (empty, `//`, a query, a fragment, a space, `%`, `..`, a name that starts with a digit) is an error that names the variable, not the value. At most 200 pairs per run.
- **The run.** The program gets every pair under its variable name, injected and redacted as before, and the ordinary values as plain environment variables (not secret, not redacted). `--reason` is always required. With neither `--secrets` nor a reference the error is the old one: "Name the secrets with --secrets NAME[,NAME...]".
- **The approval page and the passkey.** After the `Run:` line and the script blocks (so a long `.env` cannot push them out of sight) the page lists every `Env file:` path, then **one `Pair:` line per secret** (`Pair: STRIPE_KEY <- secret team/payments/STRIPE_PRODUCTION_KEY (renamed)`; `renamed` marks every pair whose variable differs from the secret's name; the `Secrets:` line still lists the store names), then one `decrypt with secret KEY: VARIABLE (cipher sha256 FINGERPRINT) from FILE` line per encrypted value (names and a 12-character fingerprint only), then **every ordinary variable with its value** (`  | LOG_LEVEL=Debug`, marked like script lines, control and bidi characters replaced by a mark). When an ordinary variable changes which code runs (a code-loading name such as `NODE_OPTIONS`, `PATH`, a proxy, a git identity), one **warning section** is shown on the page above the request text and above the Deny and Approve controls (heading "Warning: This run changes how the program loads code or where it sends data", every name with its visible value, a one-line reason per class: loads code, changes the library path, routes network traffic, changes git behaviour, and the sentence "Your approval covers exactly these values."); the same block is the `Warning:` line group in the text the passkey signs, and a remote authority shows the same section. These values are passed on to the program as written (not stripped, not refused) and are in the request fingerprint; a value the page cannot show (encrypted, or a secret reference) is still refused for such names. All of it is part of the text the passkey signs and of the request fingerprint (pairs, paths, names, values and the SHA-256 of every ciphertext). The terminal echo of the same page lists ordinary variable **names only**. The signed audit events keep names and fingerprints only (metadata: the secrets, the variable-to-secret pairs, the file paths, `decrypts` as `VARIABLE=KEY:FINGERPRINT`, never a value, a ciphertext or a key).
- **Trust: the agent can write the `.env`.** So the human approves the pairs, not the file. (1) Ordinary `.env` values that are on the code-loading list (`NODE_OPTIONS`, `PYTHONSTARTUP`...) are **passed on**: the page shows every ordinary value in full, except a value that looks like a credential (a name with PASSWORD, TOKEN, SECRET, API_KEY, PRIVATE_KEY, AUTH or CREDENTIAL in it, a password inside a URL or connection string, a bearer value, a known token shape), which it shows as `[hidden]`, and names the code-loading ones in a warning at the top of the block, and they are part of the fingerprint. The list under [How approval works](#how-approval-works) still strips what the agent's own shell supplies (the inherited environment). That list is not complete, so **the page is the control**: read the ordinary values it shows (a proxy, a CA file, a git or JVM option, an API base URL can redirect a secret or load code). (2) What the page cannot show is held to a stricter rule: a reference **or an encrypted value** whose variable is on that list, or is `PATH`, `PATHEXT`, `COMSPEC`, `SystemRoot`, `windir`, starts with `DOTENV_PRIVATE_KEY`, `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY`, `GIT_AUTHOR_` or `GIT_COMMITTER_`, or ends in `_PROXY` (case-insensitive), is refused (exit 2, before any page), and `--secrets NAME` is refused for such a name too. The rule is decided by the name alone (an environment variable of that name does not change it), the service applies it again to every request over the API, and a final filter applies it to the secrets before the child's environment is built.
- **Dotenvx projects.** Set **WITH_SECRETS_DOTENVX_EXECUTABLE** to the absolute path of a trusted dotenvx executable in the requesting user's environment. WithSecrets invokes it when a selected file contains an encrypted declaration or the working directory has an Envfile, Dotenvxfile, or Dotenv.toml. The approval identifies the project input digest and any ordinary names evaluated at launch. Literal values stay as shown in the approval.
- After approval, the requesting client runs **dotenvx run** with the full selected files. Dotenvx can use the user's private keys, project key files, and Armor configuration. If Armor emits its human-approval prompt, WithSecrets stops the launch. The helper returns only the approved dynamic and encrypted values over a private pipe. When dotenvx succeeds, the service validates the one-use response, adds WithSecrets values, and starts the app.
- Selected files must pass WithSecrets' declaration parser, which requires one declaration per line. Windows keeps existing input files open for read sharing. Linux and macOS run dotenvx from a private copy of the selected files and policy. Command substitutions on those platforms see the copy's working directory. The application uses the original working directory on every platform. Live Armor approval remains unverified.
- **Not built yet.** `${VAR}` expansion, `--env NAME` layering, a project namespace, and the host service. `secret://project/NAME` is just a folder named `project` in the global store.

## The host service

The trusted side of a run is the **host service**: `with-secrets service [--port N]` runs it in the foreground (stop it with Ctrl+C). The command line reaches it over a channel that only the current OS user can open: a **named pipe** on Windows, a **Unix-domain socket** on Linux and macOS (see "Local transport" in the architecture document). There is no port for runs. The service also serves the admin web app on `127.0.0.1` and `[::1]` only, on port 8765 by default (`--port N`, or the `WITH_SECRETS_PORT` variable; there is no stored setting for it); that port serves nothing of the command line's routes. A run is a client of it: the command line reads the `.env` files once, sends the request (names, pairs, reason, program, arguments, folder, the `.env` plan and the environment the program will inherit, with a digest over all of it) to `POST /v1/launch`, prints the approval link and the redacted output the service streams back, and ends with the exit code the service reports. The client never opens `with-secrets.db`, never decrypts and never starts the program; the service owns the approval page, the store, decryption, the program's environment, the launch, the redaction and the exit status. Reaching the API authorizes nothing by itself: no secret is opened until a passkey approved the page (or a grant that covers the exact request), and no response carries a secret. The API has no caller identity: **any local OS user (any process that can reach loopback) can reach it**, which is why a grant is not limited to one OS user: that is an open limit (see Known limits), not something this version enforces. The environment the program inherits is part of what is approved: the page shows how many variables there are and the names of those that change which code runs or where traffic goes (never values), and a different environment is a different approval. If the client is interrupted or disconnects after the program started, the service ends the program and its child processes; on Windows the program has a console of its own, so Ctrl+C in the service window does not reach it. At most 8 launches run at once. The API refuses a request whose `Host` is not a loopback name, that has an `Origin` header, is not JSON, is over 1 MB or slow, has an unknown field, a wrong digest or version, is expired, or reuses an id.

A run has no port option: it connects to the service of the user who runs it. If the service is not running (nothing answers on the channel), the run prints `with-secrets: the host service is not running. Start it with: with-secrets service` and exits with **6**. Windows service installation and start at logon come later; the commands for a person (`--recover`, `--needs`) still open `with-secrets.db` themselves in this version.

### Local endpoint

| Platform | Endpoint | Permissions |
| --- | --- | --- |
| Windows | named pipe `\\.\pipe\with-secrets-<user SID>` | allow: the current user; deny: network clients; the first instance is exclusive; service and command at the same elevation level |
| Linux | `$XDG_RUNTIME_DIR/with-secrets/service.sock` (when it is a private per-user directory), else `/tmp/with-secrets-UID/service.sock` | directory owned by this user, 700 (exactly; not a link), socket 600, peer user checked |
| macOS | `$TMPDIR/with-secrets/service.sock` (when it is a private per-user directory; an unset `TMPDIR` or a shared `/tmp` is not used), else `/tmp/with-secrets-UID/service.sock` | as Linux |

The service creates the directory (mode 700) when it is missing and removes its socket when it stops cleanly. A directory that exists with any other mode, that another user owns, or that is a link, is refused with the reason; nothing is changed in it. A socket file left by a service that crashed is replaced at the next start, but only when it is a socket of this user and the probe connection is refused; a file, directory or link at that path, a socket this user may not connect to, or any other probe error is left alone and the start fails with the reason. One that answers is never touched, and the second service does not start. The socket path must be at most 100 bytes (platform limit about 104). If the channel cannot be made the service does not start and a run never falls back to a port. With nothing on the channel a run exits **6**; with something that is not this machine's service on it, or a channel that cannot be used safely or was refused (a directory that is not this user's, a pipe made at another elevation level), **7** (nothing was sent). On Windows the service and the command must run as the same user at the same elevation level: an elevated service is not reachable from a normal terminal, and the other way round (the refusal says "different elevation levels").

## State and audit

Passkeys, settings and secrets are kept in `%USERPROFILE%\.with-secrets\with-secrets.db`, a SQLite database in WAL mode. The manifest is canonical JSON signed by an admin passkey over `SHA-256(bind || SHA-256(manifest))`. A replacement manifest requires a signer who is an admin in both the stored and new manifests. Signed secret batches can add or replace ciphertext hashes between admin-signed manifests. Each change advances the effective version and must match the version the page started from. Sign counts are stored outside the signatures.

Every command verifies the signed state first. If verification fails, the command exits with code 4 and reports `state failed verification: delete with-secrets.db to start over (only if you did not edit it)`. A process with write access can still replace the whole database with one signed by its own keys. That state shows different [admin key fingerprints](#admin-keys).

Writes are transactional and wait up to 5 seconds for another writer. The database holds names and JWE ciphertext. A missing file is treated as an empty store. An unreadable, damaged or persistently locked database stops the command with exit 4. If a run cannot write its audit entry, it exits with code 5.

Every change to the store is an **administrative audit event**: a signed event of type `admin` (see [Audit trail](#audit-trail-of-the-host-service)) whose outcome is the event name (`secrets-set`, `secrets-removed`, `settings-changed`, `setup`, `key-enrolled`, `key-removed`, `key-rotated`, `approvals-revoked`, `recovered`, and `change-denied` for a refused or failed change with the command, the secret names and why), whose reason is a short text with the approving passkey's name (`key-enrolled` says whether the new key is an admin; `approvals-revoked` says how many were cleared), and whose arguments are names only (secret, setting or key names). It holds names, never values. The event is signed with the machine identity key and committed to the outbox (`with-secrets.db`) inside the change's own `with-secrets.db` write transaction, just before it commits: if the event cannot be committed, the change is not made. A failed transaction rolls back both the change and the event. A refused change is recorded only when `with-secrets.db` already exists. The service sends these events to the authority with the run events; you read them in the admin web app. The old `--audit` command and its log are gone.

**One file per machine.** Every machine, an authority or a remote host, keeps one database, `with-secrets.db`, with the full schema (schema version 4): the signed manifest, the secret rows, the machines, grants, providers, authority keys, the audit history and the host's audit outbox. On a remote host only the outbox tables (and the audit rows of its own `pair` command) ever hold rows. Every connection uses `journal_mode=WAL`, `synchronous=FULL`, foreign keys and a 5-second busy timeout; `PRAGMA quick_check`, the schema version and the exact table layout are checked once per open. A change and its audit event are written in one transaction, so a failed commit leaves neither. Inside one process every writer waits its turn on one gate per file before SQLite's write lock; between processes (the service, `--recover`, the first-time setup, `pair`) SQLite's 5-second busy wait decides. The first creation of the file is serialized between processes by an operating-system lock on `with-secrets.db.lock` beside it. A file of another schema version stops every command with exit 4 (`with-secrets.db is not of schema version 4; delete with-secrets.db to start over`); a folder that still holds `state.db`, `authority.db` or `audit-outbox.db` from an earlier version is refused with exit 4 (`... still holds state.db ... from an earlier version of with-secrets; delete it to start over (nothing is moved over)`). Nothing is converted or imported. Keep a copy of the old files before you delete them.

**The review key R.** The signed manifest also carries a separate P-256 recipient key pair, the **review key** `R`: its public key and its private key wrapped by `MK` (AES-256-GCM, associated data `with-secrets/v1 review` and the review public key), beside the vault of `K`. `R` encrypts only the review text of grants (the page text a passkey signed, see [Grants](#grants)); `K` never does, and `R` never encrypts a secret value. Writing review text needs only the public half. The private half is plain only in the service's memory while the authority is unlocked and review is open (see [Grants](#grants)).

### The secret store

Existing schema 4 databases gain the signed-batch table automatically on open. Older binaries that expect the previous table layout cannot open the upgraded database.

- **Rows.** Each secret is a row in the `secrets` table in `with-secrets.db`. Its value is sealed with compact JWE using `ECDH-ES+A256KW` on P-256 and `A256CBC-HS512`. Microsoft IdentityModel implements the envelope. This storage format is independent of project .env encryption.
- **Signed hashes.** The admin-signed manifest holds the store's public key and a snapshot of the SHA-256 ciphertext hashes. Each later batch signs the names and new hashes against the preceding state. Every command verifies the manifest and batches in order. Every secret store read also checks that every ciphertext matches its effective signed hash. A changed ciphertext, row without a hash, or hash without a row stops the command with exit 4 (`the secret store failed verification`).
- **One tap to save a batch.** On the Secrets page, choose **Add secret** and use **Add another secret** to enter up to 20 new or replacement values. Save seals the values in the browser. The service checks them, encrypts them to the store public key, and returns the batch for one fresh tap from any enrolled passkey. The tap binds the submitted values and the resulting ciphertext hashes. The rows, signed batch and audit event commit together if the state is still the version the page started from. Existing grants can use replacement values without asking again.
- **Removing a secret** requires an admin passkey to sign the next manifest with the retained hashes. Every admin-signed manifest incorporates the current hashes and replaces the earlier signed batches. Removing an enrolled passkey preserves the values it already saved.
- **Only the requested rows are decrypted**, with the private key passed as a parameter (never an environment variable or a file). A run with `--secrets A` decrypts `A` and no other secret.
- **The store key is wrapped at rest.** Only an admin key has a slot in the signed manifest. The passkey's WebAuthn PRF output for the slot salt gives a key-encryption key (HKDF-SHA-256), which unwraps a random master key `MK` (AES-256-GCM, bound to the credential id and salt). `MK` unwraps the private JWE store key `K` and the Review key `R`. A convenience key has no slot and can be enrolled without PRF.
- **Unlock and approval are separate actions.** The unlock page requests an admin assertion and PRF in the same prompt. The browser seals the output to the page's server key (ECDH P-256, HKDF-SHA-256, AES-256-GCM). A missing, invalid or mismatched output leaves the authority locked. An approval signs the exact command and its approved scope with user verification. It can use any enrolled key without PRF.
- **Grants cover later runs.** The service checks every run online. A valid grant within the run's exact scope lets it proceed without another tap, including on the first use of the grant.
- **Cross-platform.** There is no Credential Manager, no `.env.keys` and no Windows-only step: the store works wherever the tool runs and a PRF passkey is available.
- **A failed or abandoned first-time setup leaves no key anywhere.** The store's private key is made in memory at the first-time setup and goes only into the vault of the first manifest the new admin passkey signs, which is written in one transaction with the settings and the key. A cancelled or failed first-time setup stores nothing; storing a secret stores only ciphertexts and their hashes.
- **Memory.** The service keeps `K` and `R` in pinned memory for the entire unlock session and zeroes the arrays on lock or shutdown. It wipes temporary `MK`, key-encryption key and PRF output arrays after use and clears returned value buffers once they are consumed. Runtime strings, the child environment, and copies created by the cryptographic library may remain in memory. Software enforces the approval checks while the authority is unlocked. A program that can read service memory or bypass its checks can obtain secrets.
- **Removing a passkey does not stop it from opening `MK` using an older copy of `with-secrets.db`.** `MK` and `K` are not rotated when a passkey is removed; the rotation of the secret store key rotates them (and keeps only the tapped key). Until you rotate, a removed key with its authenticator, plus an older `with-secrets.db` copy that still has its slot and the vault, still opens the store key.
- **The PRF output crosses localhost HTTP encrypted** to the page's own server key. This protects against passive observation, for example in a tunnel that ends TLS; it does not protect against an active man in the middle who replaces the page's server key (the same limit as the secret values).

### One link per command

A command prints one link. When it has more steps (`--recover`; in the admin app, adding a passkey and the rotation of the secret store key), the page of a step that has verified (the passkey proof or the recovery code was checked) answers with the address of the next step's page, made at that moment (a new one-use token, the same server and port; the host is the admin keys' host or the `baseUrl` host, as before), and moves on by itself with the text "Step done. Continuing..." If the browser blocks that, the page shows the same address as a link and a **Continue** button. The next page needs the step before it done: its address is not known before, and each page works once. Every page keeps its own rules (a passkey prompt only in a tap, Cancel, retries, diagnostics). The command's time limit is shared by its steps, not restarted at each. Where a command ends with a code from the page (the first-time setup, adding a passkey, the new-store step of `--recover`), the terminal asks for it after every tap, and nothing is stored before it is typed. While it waits, the last thing on the terminal is `Waiting for the code from the page. Paste it here and press Enter: ` with the cursor after it; the command writes nothing else meanwhile (no line is held back or dropped; with `--debug` the diagnostic lines print as they arrive). The first-time setup is one page too (its Step 2 button signs the new state on the same page), like removing a passkey.

If the reply of a step that verified is lost on the way, the page sends the same request again and gets the same reply (the same next address or the same code), which makes no second page and no second code; the program keeps that reply only in memory until the command ends, and a different request after the decision gets 404. If the page still did not move on, press Ctrl+C and run the command again. A page whose step is gone says so in a short text (404) and points to the terminal.

### The recovery code

- **The first-time setup shows a recovery code, once.** It is 8 groups of 4 letters and digits (for example `ABCD-EFGH-JKLM-NPQR-STUV-WXYZ-2345-6723`), shown on the last page together with the 6-digit code, in the page only (never in the terminal, a log, the audit log or `with-secrets.db`). **Write it down and keep it offline**, apart from this computer. **Anyone who has the code and `with-secrets.db` can open all your secrets**, so keep it as private as a password. Typing it accepts lower case, spaces and dashes.
- **What it is.** 20 random bytes. `RK = HKDF-SHA-256(code, salt, "with-secrets/v1 recovery")` opens the **recovery slot** in the signed manifest: `MK` wrapped with AES-256-GCM under `RK` (12-byte nonce, the store public key as associated data). `MK` then opens the vault, like a passkey's slot does.
- **`with-secrets --recover`** is for when every passkey is lost. Page 1 (the only link the terminal prints) asks for the code (the browser encrypts it to a key that exists only for that page, like a secret value; three wrong codes end it, and a refusal changes nothing). The page then moves on by itself (see [One link per command](#one-link-per-command)) to a first setup on a new, empty state: you create a **new passkey** (and can change the settings), and the new master key, store key, vault and **recovery code** are made. The secrets are decrypted with the old store key and encrypted again for the new one, one at a time, and everything is written in one transaction. Recovery keeps a snapshot at `with-secrets.db.recovered-<UTC yyyyMMddHHmmss>` and updates the secret-store tables and recovery audit events together in the live file. Machine, grant, provider and audit history tables stay in the live database. The review key `R` is carried over: the code's `MK` opens the old `R`, and the new manifest holds the same review public key with its private key wrapped by the new `MK`, so no grant's review text changes (the grants still stop being usable, because their approving passkeys are no longer enrolled). **The old admin keys are gone** from the new state; add them again as passkeys in the admin web app. Any failure leaves the old `with-secrets.db` as it was. It works while the old keys still exist, too. The old recovery code does not open the new store.
- **Rotating the secret store key** (admin web app, Settings, **Secret store key**) makes a new store key `K` and master key `MK` and encrypts every secret again. Tap 1 is an admin approval that also releases the PRF output of the key you tap (the page lists the keys that will be removed); tap 2 (**Step 2 of 2**, reached from the page after tap 1; the terminal prints no second link) has the same key sign the new state, including the hashes of the new ciphertexts. **Only the key you tap stays**: every other key is removed, because their slots wrap the old `MK` and would still open an older copy of `with-secrets.db`. Add them again as passkeys. A new recovery code is shown once on the last page and the old one stops working. The rotation also makes a new review key `R`: in the same transaction every grant's review text is decrypted with the old `R` (opened by the same tap's `MK`), encrypted to the new one and its grant row sealed again; a grant whose seal does not verify loses its review text and seal. While the authority is locked the rotation is refused and nothing changes. Review is closed afterwards (tap to review again). The change is one transaction (with a `key-rotated` audit entry naming the removed keys); a failure or a timeout between the taps changes nothing. A key that has a slot is required.
- **Compare the fingerprint before you type the code.** `--recover` and the rotation of the secret store key print the old store's admin fingerprint line (`Admins: laptop ab12 cd34 ef56 7890`, the same as on every page) in the terminal of the command, or of the service for the rotation, before the link, and tell you to compare it with the one you wrote down. If it differs, do not type the code or approve: the state was replaced. Why: a typed recovery code is not tied to the page's origin the way a passkey tap is, so a look-alike page can read it; only the fingerprint, checked against your own note, tells you the page belongs to your store.
- **Rotation does not help if the kept key's PRF output may have leaked** (a tap on a look-alike page, a memory read during a run): the leaked output still opens the new master key, because the kept key keeps its slot salt. After such a doubt, tap a key that was never used on a doubtful page, or rebuild the store with `--recover` on new keys.
- **Show-once.** The new recovery code is shown on the last page only once. If the page did not show it (lost connection), the old code is already dead after the rotation: rotate again. After the first-time setup or `--recover`, rotate to get a new code.
- **Rotating does not recall values that were already exposed.** An older copy of `with-secrets.db` plus an old key, or an old recovery code, still opens the secrets it held. Rotate the secrets themselves at their source (the service that issued them) as well.
- **No migration.** A `with-secrets.db` of another schema version is not moved forward: delete it and set up again (`with-secrets admin`), then store the secrets again in the admin web app.

## Admin keys

At least one enrolled passkey is an **admin key**. The first passkey created in setup is an admin key. To enroll another, select **Also make this key an admin**. The approving admin passkey signs that choice as part of the new manifest. Any enrolled passkey can approve runs and save secret values while the authority is unlocked. Changes to settings or passkey enrollment and removal of secrets require an admin passkey.

- **Use two admin keys**, for example your laptop and your phone. Then a lost or broken device is no emergency: the other admin key removes it on the **Passkeys** page of the admin web app.
- **To replace an admin key** (a new device): add the new key on the **Passkeys** page, tick **Also make this key an admin**, then remove the old one there, approved with the new key (an admin key cannot approve its own removal).
- **After a reset, delete the old `localhost` passkeys in your password manager.** Each passkey is labelled `with-secrets <name> <random guid>` (the name is cut first if the label would pass 64 characters); the label is only for display.
- **The last admin key cannot be removed.** With a single admin key and that device lost, nothing can change the state any more: delete `with-secrets.db` and run `with-secrets admin` again (your passkeys, settings and secrets start over: the secrets are in `with-secrets.db` too, so store them again in the admin web app).

### The fingerprints

An admin key's fingerprint is the first 8 bytes of SHA-256 of its public key (as stored in the manifest), written as four groups of four hex digits. Every admin key is listed, oldest first: `Admins: laptop ab12 cd34 ef56 7890, phone 1234 5678 9abc def0`. It is not secret. The line is shown:

- on every page the tool serves: run approvals, adding and removing passkeys, secret changes and the rotation of the secret store key (on an approval page it is part of the text your passkey signs);
- once when the first-time setup finishes, and when adding a passkey shows its code, on the page and in the terminal.

Note the fingerprints down when you first see them, and check the line on each page before you approve. **If it ever changes without you adding or removing an admin key, the state was replaced**: someone deleted `with-secrets.db` and set up their own admin key, or an admin key was added that you did not add. Do not approve anything; find out what happened, then delete `with-secrets.db` and set up again with `with-secrets admin`. The fingerprints do not stop a same-user agent from resetting the database; they make the reset visible to you. Restoring an older copy of `with-secrets.db` (with your own admin keys) is not detected: it can bring back passkeys you removed (an admin key you removed too) and settings you changed, and old secret values, including one you replaced after it leaked (so rotate a leaked value at its source, not only here). Nothing recalls a secret a program already saw: rotate any value that may have leaked.

## Where the page can be reached

The authority browser interface is at `https://with-secrets.localhost:<port>` on the authority. Set up its leaf as described in [Operations](operations.md#browser-https-certificate). Use `with-secrets service --port N` or `WITH_SECRETS_PORT` to select the browser port. Approval links use this origin. The terminal recovery command can select its own listener port with `--port N`. The relying-party ID remains `with-secrets.localhost`.

## Settings

The settings are kept in `with-secrets.db` in the protected folder, not in an environment variable or flag, because the agent controls those. They change only in the admin web app (**Settings**, **Approval pages**):

- **Save** is approved with your admin passkey, which signs exactly the new state: the challenge is `SHA-256(bind || SHA-256(manifest))`, the manifest being the current one with the new values and the next version. The program checks the passkey, then writes the new manifest and an audit entry (the names of the settings that changed, old -> new, and the key; none of the settings is secret) in one transaction. A state that changed meanwhile, a wrong proof or a value out of its limits changes nothing.
- The first-time setup (`with-secrets admin` with nothing enrolled) uses the defaults. There is no way to save settings without a passkey.

With nothing enrolled every setting has its default. A manifest with a value that cannot be used never verifies, so it stops every command with exit 4.

| Setting | Default | Meaning and limits |
| --- | --- | --- |
| `reuseMaxMinutes` | `43200` | Ceiling for the finite durations offered on new approvals. 10 to 43200 minutes. Existing signed settings retain their values |
| `timeoutMinutes` | `15` | How long a request waits for an answer. 1 to 30 minutes. Existing signed settings retain their values |

## Approval reuse

**Approve once** records a consumed grant and covers only that launch. Choose a duration from the arrow beside it to approve the current run and allow the same command to run again. Choosing the duration opens the passkey prompt. Use `with-secrets approve ...` to create a reusable grant without launching the command.

## Rules

- **Terminal output is public.** The agent reads it. Nothing the program prints is secret: it shows links, names, and results, never values or key bytes.
- Run `with-secrets admin` (first-time setup) and `--recover` only in a terminal you own. Values are typed in the browser, never in a terminal. The terminal verification code appears in the browser and you enter it in that terminal. Quick Start checks it before passkey creation.
- **Only type a confirmation code that a page you opened yourself shows.** If the page has already ended or shows no code, press Ctrl+C. (An agent that holds the link could register its own key and pass you its code.)

## Logging

Normally the terminal shows only what a command always showed: its result, errors, links and the code prompt. The lines that explain what the program is doing (`with-secrets: connection opened (3 s)`, `request POST /proof (headers read, 3 s)`, `proof received (N bytes)`, `proof checked: accepted`) are Debug events and are not shown.

- **`--debug`** (with any command, before `--`) or **`WITH_SECRETS_DEBUG=1`**: those lines print on the terminal as they happen, and are also written to the log file.
- **Log file:** `%USERPROFILE%\.with-secrets\logs\with-secrets-YYYYMMDD.log`, one file a day, rolled at 1 MB, the newest 7 files kept. The folder is made when needed; if the file cannot be opened or written, the command goes on without it.
- **Always in the file, without `--debug`:** warnings and errors: a request handler that failed (the exception type name only), a request body that timed out, a state that failed its check, an audit row that could not be written.
- **Nothing secret:** the log holds route words (`page`, `proof`, `save`...), sizes, whole seconds and exception type names. Never a link or token, a request body, a key, PRF output, a code or recovery code, a secret value, a `.env` value or exception text.

## Troubleshooting

If a page sits on "Checking your passkey..." and then says the program did not answer, run the command again with `--debug` (or set `WITH_SECRETS_DEBUG=1`) and look at the terminal and the log file (see [Logging](#logging)). `with-secrets: connection opened (N s)` and `request POST /proof (headers read, N s)` (a method, a route word and whole seconds since the link was made, never the link, a body or a key) show that the request reached the program; `body slow` means its body was still arriving after 5 seconds; no line means it never arrived. The page adds a `Diagnostics:` line after a failed post (never after a success), with times only: when it was opened, when the passkey prompt started and answered, how long the page was hidden, each attempt, and whether the phone was online. Send those lines, not a screenshot of anything secret, when you report a problem.

If every command stops with exit 4 and says the folder still holds `state.db`, `authority.db` or `audit-outbox.db`, or that `with-secrets.db` is not of schema version 4, the folder is from an earlier version: nothing is converted. Keep a copy, delete those files and set up again (`with-secrets admin`). A grant marked "This grant is not verified and is not used" (after an authority key recovery, a removed approving passkey or an edited row) is never used: approve the command again.

## Grants

**When to choose a grant with no end.** Anyone with an enrolled passkey, admin or not, can explicitly approve one for a standing job that would otherwise need repeated approval. Each new run still needs a successful authority check for the same approved scope and records a signed authorization event. A timed grant adds a scheduled point to reconsider access. An enrolled passkey can revoke either kind at any time to stop new launches under the grant. Credentials already delivered remain subject to the provider's own expiry and revocation rules.

`with-secrets approve --secrets NAME[,NAME...] --reason TEXT -- PROGRAM [ARGS...]` takes the same arguments as a run, shows the same approval page, and on **Approve** makes a **grant** for that exact request instead of running it (nothing is decrypted, nothing starts). The page can offer 1, 2, 4, 8, or 24 hours, 7 or 30 days, or **Always**. The signed reuse setting caps the finite options. A later `run` of a request in the same scope (the same arguments, secret names and pairs, resolved program, working folder, script contents and inherited environment, and the same machine) is covered by the grant: no approval page decision is needed, and the run says so in one line. Anything else (another program or secret, an edited script, an ended or revoked grant) goes through the normal page. A grant has its own scope key (machine, request fingerprint and the **full argument list**, so `python -c ...`, `bash -c ...` or `node -e ...` inline code is part of it): a grant for one command line never covers another. The approve page is headed as creating a grant, says that no program runs, and what it covers.

An admin unlock makes the store key available for subsequent runs. Every use of a grant checks the authority online before reading values. Locking or restarting the authority clears the keys from memory. Revoking a grant, removing a signer or invalidating a machine prevents future uses of the grant.

In the admin web app, **Access → Grants** shows the command, machine, status and end time for unexpired grants. Select a row to see its full program, folder, secret names, grant ID and available actions. Each grant shows its usage ("Used once" for a once-only grant) and its state; a once-only grant is "Used" (status `consumed`) from the moment the approval is recorded, before the run starts, and it stays consumed even if the run then fails to start. Its buttons start **Extend** (move the end of an active grant later, N minutes from its present end, 1 to 1440, or give it no end), **Allow repeat runs** (choose an approval duration to extend the existing once-only grant for the same command and scope. The grant keeps its ID) and **Revoke** (end the grant now; a connected host is told at once and cancels launches that have not started). Extend and Allow repeat runs require a fresh tap from an enrolled passkey with user verification. In an active admin session, Revoke needs only confirmation. A grant that changed while the dialog was open is refused. The old `admin grant ...` commands no longer exist. None of them changes the machine's security revision. A revoked or invalidated grant cannot be extended or renewed. A used once-only grant can be extended for repeat runs. Expired grants drop out of the screen when the list refreshes. Their records remain available through the grants API, including the renew operation, and their audit history is preserved.

**A host whose authority cannot be reached fails closed.** There is no offline lease and no offline use of a grant. Every run asks the authority (a grant is checked with it on every run); when the authority cannot be reached, or does not vouch for the machine, nothing is decrypted and nothing runs, whatever the host synchronized earlier. The host is vouched for only while its last verified check-in with the authority said the machine is Trusted and its host name is the bound one; that state lives in memory only, a restart destroys it, a changed or replayed check-in answer vouches for nothing, and changing the system date does not matter. A host makes no new approval, extension or renewal while the authority cannot be reached. A connected host applies a revocation or a disable at once. After a restart the service checks in with its authority before it accepts a request (it answers 503 until then, which a run reports as exit **9**: ask again in a moment).

A grant row is backed by the person's passkey assertion over the page text (scope, security revision, minutes); an extension, renewal or replacement is backed by an enrolled passkey's assertion over the exact change. The authority verifies that assertion when it writes the row, then stores the **page text encrypted to the review key `R`** (it holds the full command line, so it is never kept in clear) and **seals the row** with the authority signing key in the same transaction: the seal covers the grant's fields, the evidence kind, nonce and minutes, the hashes of the proof and of the encrypted text, the review public key and the authority key's fingerprint. At every use the authority checks, without decrypting anything, that the seal verifies against the active authority key as the key store holds it, that it names the current review public key, and that the original approving passkey and the last changing passkey are still enrolled. A row that fails (planted, edited, a seal copied from another row, a revoked row set active again, its approving passkey removed, sealed by a retired or recovered-away authority key) is not used and not offered for any action; the audit says why (`grant {id}: the seal does not verify` and similar). A routine authority key rotation reseals every verified grant; a key recovery does not, so every grant then shows "not verified" and a person approves again. A revoked or invalidated grant keeps no review text and no seal.

**Review text.** While the authority is unlocked, **Review** in the Grants view shows the plain text of the page the passkey signed. Any enrolled passkey's session can read it with `GET /api/v1/grants/{id}/review` (state `open`, `locked`, or `none`). Lock and restart close Review. Rotating the store key also locks the authority. Review text stays out of logs, audit rows and errors.

## Audit trail of the host service

The audit views show a verified passkey's stable credential id, display name and kind. The entry labels the key according to its role. Sign-out and queue denial use the key that opened the session. A grant-covered run shows the grant's approving key and any different key that last changed it. Secret delivery records the admin key that unlocked the authority. A name can be reused by a different credential, whose id will be different.

The host service keeps a **signed audit trail**; it is the only audit log. Besides every run it does, it holds the administrative events of the human commands and the admin app (see "Administrative events" below). Each run produces separate events: the **authorization** decision (approved on the page, covered by a grant, or denied with a reason code), the **launch** outcome (started, or why not) and the **execution** outcome (the exit code). An event has a unique id, a per-machine sequence number (1, 2, 3, ... with no gaps), a time, the machine fingerprint, the working folder, the program, the arguments, the grant id when a grant was used, and a signature by the machine identity key. It never holds an OS user name, a secret value or an environment value; arguments are recorded with values that look like secrets masked (a value after `--token`, `password=`, `Authorization: Bearer`, the password of a URL), and anything very long is cut (a folder or program path over 4096 characters is cut host-side, with a marker, so the authority never refuses the event of a run that went ahead).

The authorization event is committed to the host’s outbox tables in `with-secrets.db`, **before** a run decrypts anything. If it cannot be committed (the disk is full or the file is damaged), the run does not happen: exit **5**. The launch and execution events come after the fact, so a failure to record them is only logged. The service sends the outbox to the authority by itself and keeps retrying until the authority has stored the events and signed an acknowledgement; only then are they removed locally, and a launch never waits for the upload. The authority checks each machine signature, stores each event id once, notes any hole or reused number in a machine's sequence (it never refuses an event for that) and keeps events for its retention (365 days unless the authority is told otherwise; 0 keeps everything). There is no hash chain and no export.

**Administrative events.** A change to the secret store, the passkeys, the settings or the store itself (also a refused one) is an event of type `admin`: its outcome is the event name, its reason carries the approving key's name, and its arguments are the secret, setting or key names; never a value, a code or key material. Every event can also carry a small signed **metadata** object (names and fingerprints only): a run's authorization event lists the secret names, the variable mapping, the `.env` files, the file fingerprints, the approving key and the reuse minutes; an administrative event lists the full detail, the key and the names. The admin app shows it as read-only text. Each change and its outbox event commit in the same SQLite transaction. The event is signed, numbered and uploaded as a run’s event is (the commands write it to the same outbox with the machine identity key, and the service uploads it; if no service runs, it waits in the outbox). Filter by type `admin` in the admin web app.

The history is read in the **admin web app** (`/api/v1/audit/events`). Sign in for arguments, detailed audit entries, and text search. Filters: machine (fingerprint start), project (working directory), time range (since, until), type (authorization, launch, execution or admin), authorization or launch/execution outcome, grant id, text, and how many (1 to 1000); a **gap view** lists the holes. It is read-only. Restore a compatible backup if the shared database is damaged. Limit: a process of the same OS user can still delete the outbox or tamper with `with-secrets.db`; the trail does not prove that a compromised host reported truthfully.

## Remote authority over mutual TLS

A host service can use a **remote authority** instead of the local one, with no change to the CLI or the local API. The host connects **directly** to its one configured authority over HTTPS: **TLS 1.3 with a certificate on both sides, and HTTP/2**. There is no relay, no custom handshake and no application-level encryption (the TLS channel is the encryption); TLS 1.2, HTTP/1.1, plain HTTP, session resumption and 0-RTT are not offered, and a client that cannot do TLS 1.3 gets no connection. `host.json` (public data only) selects it and keeps the address and the authority's identity apart:

```json
"remote": { "endpoint": "https://127.0.0.1:8790", "authorityIdentityFingerprint": "<64 hex digits>", "authorityIdentityCertificate": "<base64 DER>" }
```

The address is routing information only. **Who the authority is** is its identity certificate: every machine has one persistent self-signed identity certificate (`machine-identity.cer` beside `host.json`, made from the machine's CNG identity key, ECDSA P-256, ten years, a CA with path length 0 per architecture 10.2, key usage DigitalSignature and KeyCertSign). A running instance also makes a **temporary certificate**: a fresh in-memory TLS key and a 24-hour leaf signed by the identity key (SAN `urn:with-secrets:machine:<fingerprint>`, serverAuth and clientAuth), replaced an hour before it expires; the same certificate is the authority's server certificate and a host's client certificate. Each side validates the other only against the one enrolled or configured identity certificate (signature, dates, not a CA, key usage, both purposes, the machine named in the SAN); the operating system's trust store and the host name in the address are not consulted. On Windows the in-memory TLS key is a named, non-exportable CNG key that is deleted when the process ends, because the Windows TLS stack (SChannel) cannot use an ephemeral key; a process that is killed leaves such a key behind in the user's key store (harmless: it is a private key nobody can use again, and no certificate is trusted because of it).

**macOS takes no part in machine transport.** Machine transport is TLS 1.3 only. .NET has no server-side TLS 1.3 on macOS, so a macOS machine cannot be an authority (`with-secrets service --machine-port` refuses to start there). Its client side has TLS 1.3 only behind an opt-in backend (`System.Net.Security.UseNetworkFramework`) that aborts the whole process, uncatchably, when a peer closes a connection while the client is writing ([dotnet/runtime#136439](https://github.com/dotnet/runtime/issues/136439), open in 10.0.13; a fix is in progress in [#134260](https://github.com/dotnet/runtime/pull/134260)), which is exactly what a rejected client certificate does. So a macOS machine cannot be a host of a remote authority or pair with one either: `with-secrets pair` and a `host.json` that names a remote authority refuse with this reason. Nothing falls back to an older protocol and the opt-in backend is not switched on. macOS runs with-secrets locally (its own store, approvals and runs). To use a macOS machine with an authority, run the authority and the paired hosts on Windows or Linux. This is to be revisited when the runtime fix ships (the Node-based client test in the unit suite is ready to be switched on for macOS then).

The authority listens on **its own port, separate from the loopback browser and client APIs**: `with-secrets service --machine-port 8790` (loopback by default; `--machine-bind ADDRESS` names one other address; 0.0.0.0 and `[::]` are refused). A service started before the authority has a signing key (it is made by the first approval) has no machine listener yet and starts it by itself as soon as that approval makes the key: no restart, the same address, the same rules about who may connect. Every route needs the client certificate and the machine's identity comes only from it, never from a header or a field; a machine that is not Trusted now (Pending, Disabled, Untrusted) is refused on every route and its connections get GOAWAY and are closed after a short grace; a locked authority serves nothing. A machine whose certificate is well formed but not enrolled can reach **only the pairing route**, which serves the one-time invitation protocol (see Pairing in docs/operations.md). Answers carry `Cache-Control: no-store`, are never compressed, are UTF-8 `application/json` only, and errors are a short code with a correlation id and nothing else; request size, concurrent requests and time are bounded and excess is refused rather than queued. The host follows no redirect, uses no proxy, has no fallback and backs off exponentially with jitter. A request is retried under the same id (the authority answers once); **a secret release whose answer is lost is never retried**.

Invalidations and grant events keep their sequencing, acknowledgements and revision rules, carried by an HTTP/2 **long poll** (one outstanding poll per host; no heartbeat, no periodic empty polling). On every reconnect the host authenticates, checks status and revision and purges what it holds if the revision differs. The signatures on authority-issued records and machine-signed audit events are unchanged. A host that has no authority signing key pinned asks the authority for it over the identity-pinned connection once the authority trusts the host, and pins it in `host.json`.

A host is introduced to its authority by **pairing**: `with-secrets pair` (see [Pairing a machine](#pairing-a-machine)). The old `--authority-fingerprint`, `--machine-cert` and `relay` command and the reserved `admin https://AUTHORITY` form are gone.

### Pairing a machine

A machine joins an authority with a **one-time invitation** that the administrator creates in the authority's admin web app. Nothing is typed into a URL, an argument or a request: the invitation is a credential bundle (`wsp1;https://HOST:8790;ID;CODE`: the authority's address, a unique identifier and a 128-bit random code) shown **once** and never stored in readable form.

1. **Administrator, on the authority.** Admin app, **Machines**, **Add a machine**, **Continue to passkey** (the passkey page opens by itself). The passkey page names the authority address and says the invitation is valid 10 minutes (fixed, not configurable) and registers one machine. After the tap the bundle is shown once in that dialog; copy it (if the page was closed before it was collected, it is held for 5 minutes and then lost: revoke and create another). The Invitations table at the top of Machines shows each invitation and its status. Select a pending invitation to revoke it with a passkey tap. The authority needs a machine endpoint (`with-secrets service --machine-port 8790`), because that address goes into the bundle.
   An authority restart expires every pending invitation immediately because its authentication key lives in memory. Create a new invitation after restart, even if the normal ten-minute window is still open.

2. **New machine.** `with-secrets pair` asks for the bundle at a **hidden prompt** (nothing is echoed). Unattended, supply it instead through **`WITH_SECRETS_PAIRING_FILE`** (a path to a file holding the bundle; a Docker secret is mounted at `/run/secrets/with-secrets-pairing`, which is read with no variable at all) or **`WITH_SECRETS_PAIRING`** (the bundle itself; the least safe, because a process environment is easy to read). A file beats the variable. The command removes both variables from its own process once read, and the host service never passes them to a program it starts.
3. **The protocol.** The first request carries only the invitation id and a fresh nonce, on a connection made with a throwaway identity, so nothing about this machine is shown yet. The authority answers with its public identity certificate, a nonce and an HMAC-SHA-256 proof that binds the invitation, its own fingerprint and both nonces, computed from a key derived from the code. The machine checks the certificate profile, that the TLS certificate it just saw is that identity's, and the proof, **before** it sends anything about itself. Only then does it open a fresh TLS 1.3/HTTP/2 connection pinned to that identity certificate and register: its identity certificate, fingerprint, host name, a proof of possession (a signature by its identity key) and a registration HMAC. The code is never sent; the authority stores only a protected derived key and wipes it when the invitation ends.
4. **What the machine prints.** Its fingerprint and host name and that it is **Pending**. It cannot ask for secrets or make grants.
5. **Administrator.** The machine appears under **Machines** as Pending with its fingerprint and host name. Compare them with what the machine printed, then **Approve** (its own tap). After that the host pins the authority's signing key by itself and runs.

Rules worth knowing: an invitation works once (concurrent claims have exactly one winner; a retry of the identical registration after a lost answer returns the same result); a wrong, expired, used or revoked invitation all get the same refusal; five wrong proofs withdraw an invitation, and thirty refused attempts in ten minutes make the route answer "too busy" to everyone for a while; pairing a machine again while it is Pending refreshes its record, but a Trusted, Disabled or Untrusted machine is never changed by pairing (and the invitation is not used up); at most 32 machines may wait for approval, 4 under one host name, 8 invitations may be open and 4 registrations run at once. Every creation, attempt, refusal, expiry, consumption and approval is in the durable audit with no code or proof.

### The WSL path: the authority holds the store

For a host service in WSL that uses the Windows authority: `WSL client -> WSL host service -> mutual TLS 1.3 / HTTP/2 -> Windows host service and authority`. The **authority holds the data store**: the approval page, the passkey tap and the decryption happen on the Windows side; the WSL host service shows no page, reads no store and holds no key. The values come back only on the authenticated connection as a signed, one-time delivery (never to the CLI, never in a log, never on the host's disk); the host builds the child's environment and starts the program. A failure, a disconnect, a lock or a withdrawal of trust before the delivery means nothing runs. The CLI prints the authority's page link, which you open on Windows. Saved approvals are off in remote mode; grants work.

Not built: LAN or remote deployment guidance and an administration interface beyond loopback (deferred); creating a grant from a remote host (`approve`); the real Windows-authority / WSL-host run is not completed yet (the Linux machine key store is an owner-only file, weaker than CNG; see `docs/operations.md` section 8).

## Secret providers

A **mounted secret** is a name the authority serves from a provider instance instead of the native store (architecture 10.3). The provider core is built and wired into the authority's runs (local mode: this machine's service; remote mode: the authority's service, so a host in WSL gets mounted values from the authority like native ones). **No provider adapter ships yet, and there is no way to make an instance or a mount**: their configuration formats and admin screens come with the next plan. Until then every name is native and runs behave exactly as before.

- **Names.** A mounted name has the store-name syntax (`TOKEN=secret://team/dev/GITHUB` asks for `team/dev/GITHUB`). The longest matching tree mount, or an exact individual mount, selects it; it then never falls through to another mount, the native store or an environment variable. A native secret of the same name is shadowed.
- **Approval.** The page labels mounted names with their provider instance (for example `team/dev/GITHUB (vault-one)`) and native names with `global`. Both use the same passkey approval and unlocked store key. Cached values are decrypted on the authority.
- **Freshness.** Per instance, `MaxStaleDuration` (0 to 24 hours in whole seconds; default 0; a larger value or a fraction of a second is refused, never cut or rounded). A cached value younger than 75% of it is served without asking the provider; otherwise the provider is asked, and on a final `Unavailable` or `RateLimited` the cached value is served **stale** while it is at most `MaxStaleDuration` old (measured from its last successful retrieval). Never for an authentication, access, missing-secret, configuration, response or unknown error. With 0, every run asks the provider and WithSecrets skips cache reads and writes. Disabling the cache deletes its active rows. On first opening an older database, WithSecrets clears the provider cache and switches existing providers to live retrieval. Re-enable caching explicitly per provider if needed. Older backups and disk snapshots may contain cached ciphertext. A background pass every minute refreshes rows that reached 75%; one that failed waits 1 minute, doubling to 15, and an authentication, interaction or access error halts it until an on-demand success.
- **Retries.** At most 3 provider calls per request (waits of 200 ms then 400 ms; a provider's `RetryAfter` is honoured up to 2 s), only for `Unavailable` and `RateLimited`, within 10 s per instance batch. Not configurable.
- **Failure.** Any mounted name that cannot be delivered fails the whole run closed (exit 4, the name and the error kind, never a value); nothing starts. When caching is enabled, a fresh value that cannot be written to the cache (for any reason other than the authority being locked) fails the run closed too. A failed run discards held grant keys, so after a provider outage the next run needs a new passkey tap: in local mode the grant key this host held; in remote mode the authority drops the held grant keys of every machine, not only the one that ran (keeping the key across a transient `Unavailable` is planned).
- **Mount changes end approvals.** Adding a mount that takes over a name (a native name, or one a broader mount served) and removing a mount both end every active grant that names such a name (the host is told and drops it): the name now resolves to a different secret, so it needs a new approval. Removing an instance also deletes its cached values; the background pass deletes cached values that no mounted name refers to any more.
- **Locked.** While the authority is locked no cache row is served, signed or refreshed, and a run that names a mounted secret fails closed (`the authority is locked, so no mounted secret is delivered`); a run of native names only is not affected.
- **Integrity of the configuration.** A cached value is sealed by the authority signing key as the key store holds it, so a write to `with-secrets.db` cannot plant a value of its choosing (a planted row, or a planted `authority_keys` row with its own key, is never served). The instances, mounts and namespace entries are **not** sealed (like grants and machines). So a process that can write `with-secrets.db` can redirect an approved name to another secret the instance can read: (a) change the entry's `external_id` to another external id of the same instance; (b) change the mount's `instance_id` or `base_path` to point the name at another instance or provider path; (c) change only the entry's `provider_path`, so the next retrieval stores secret B under A's external id and every name that refers to A is then served B from the cache. Binding these changes to an admin tap (all three tables, `provider_path` included) comes with the next plan.
- **Audit.** One signed event per mounted name of a run, type `admin`, outcome `provider-fresh`, `provider-cached`, `provider-stale` or `provider-failed`, with the path, the instance id and name and the error kind, and no value, ciphertext, credential or provider id. An adapter's invalidation is `provider-data-invalidated`, with the instance, scope, mount ids, the provider's external ids, paths and counts (no value). The retrieval events of one run are committed together; if they cannot be, the run fails and nothing is delivered.

**Provider tables in `with-secrets.db`.** Four provider tables beside the machines, keys, grants and audit: `provider_instances` (id, unique name, provider type, configuration JSON, `max_stale_seconds` 0 to 86400, revision), `mounts` (id, instance, kind `tree` or `single`, logical path, provider base path; one of each kind per logical path), `namespace_entries` (per mount: logical path, provider path, the provider's external id, description and its source `provider` or `local`) and `provider_cache` (one row per instance and external id: the JWE ciphertext of the value for the store's public key, `last_verified` in UTC ticks, that public key, the authority key fingerprint and a signature). The signature is the active authority signing key's over `with-secrets provider cache v1`, the instance id, the external id, `last_verified`, the SHA-256 of the ciphertext, the store public key and the key fingerprint, one per line. A row that does not verify against the active key, or names another store key, is never served (it is fetched again); so rotating the authority key, or the store key, empties the cache in effect. The configuration rows are not signed (as grants and machines). Only the authority service writes provider data (the guard against an in-flight retrieval racing an invalidation is in its memory).

## Known limits

- **The page shows the code, but only so much of it.** It shows the whole command line, the inline code, and the first 200 lines (at most 16 KB) of each script file, with a `...cut` notice when there is more. A long or obfuscated script can still be hard to judge, and an agent can write a script that prints `$DB_URL` in a form that is not redacted. Approve only code you have read and understood.
- **Interpreters are allowed in one strict form only.** Options are not parsed: anything else is refused with "put options inside the script file". Program names are matched without regard to case; an argument with leading or trailing whitespace is refused.
  - `sh`, `bash`, `zsh`, `dash`, `ksh`, `fish`, `python`, `py`, `python3`: `PROG script [args]` (the first argument does not start with `-`) or `PROG -c CODE [args]`. Not allowed: `-`, `-l`, `--login`, `-e`, `-m`, `-u`, `-W`, `-X`, `-I`, `--`, combined flags.
  - `node`, `perl`, `ruby`: `PROG script [args]` or `PROG -e CODE`. Not allowed: `--env-file`, `-C`, `--require`, `-M`, `-I`, `-E`, `--test`, `--`, combined flags.
  - `powershell`, `pwsh`: `-NoProfile` (required), `-NonInteractive`, `-NoLogo` and `-ExecutionPolicy` with one of Bypass, RemoteSigned, Unrestricted, AllSigned, Restricted, Default, Undefined (each at most once, any order), then exactly `-File path [args]` or `-Command CODE` (one code argument), written in full and in any case. The `-File` path may not contain `[`, `]` or a backtick, in the script name or its folder (PowerShell reads it as a wildcard): run from another folder. Not allowed: abbreviations (`-f`, `-c`), a bare positional, `-EncodedCommand` in any form (`-e`, `-ec`, `-enc`), padded flags, flags starting with an en dash, em dash, horizontal bar or minus sign, and code on standard input.
  - `cmd`: `cmd /d /c TAIL` (or `/k`, `/r`; `/d` is required) where every word of the tail has only letters, digits and `. _ : \ / -`, and the first word is a `.cmd` or `.bat` file written with its extension, or `echo`, `dir`, `type`, `ver`. The script path itself may contain spaces and brackets (the working folder is written in full), but a folder name with a quote or one of `% ^ & | < > !` is refused for cmd. Not allowed: `/c` without `/d`, `/s` and other switches, quotes, spaces in a word, `% ^ & | < > !`, a name without an extension (PATHEXT lookup).
  - An interpreter with nothing to run (`bash`, `python`, `cmd`, `pwsh` alone) is refused: it would read code from outside the approval. The script an interpreter names must exist and be at most 1 MB; the page, the fingerprint and the file lock all use that one operand.
  - Any other program has no analysis: the page shows its `Run:` line; a first file argument is only guessed and marked "guessed from the arguments, not verified"; a program that is itself a text script (`.cmd`, `.bat`, `.ps1`, `.sh`, `.py`, `.js`, `.pl`, `.rb`) is shown and hashed with its arguments unparsed.
- **Limits that remain.**
  - Where the system cannot lock a file (Linux, macOS, WSL), the program runs a private copy of each shown script. The copy's folder also holds a link for each entry of the original's folder (none when that folder has more than 1000 entries), so what a script finds by its own location (`dirname "$0"`, `BASH_SOURCE`, Python's `Path(__file__).resolve().parent` and `sys.path[0]`, `require('./x')`, `$PSScriptRoot`) is found as before. What is **not** the same: `$0`, `BASH_SOURCE`, `__file__` and `$PSScriptRoot` are the copy's path (the file name is the same); `..` from the script's folder is the private folder, not the original's parent; the copy's folder cannot be written, so a script that writes a new file beside itself fails (writing to a file that already exists beside it works, through its link); and what a script loads through those links is the neighbour as it is when used, not what was shown or approved (see the next item). On Windows the file itself runs, held against changes, and every path is the original's.
  - **What an approval covers.** The file or files shown (the script, and a program that is itself a text file), their hashes and the fingerprint: nothing else. Files a shown script loads (`source`, `import`, `require`, dot-sourcing, `-m` modules, `bash -c` code that runs other files) are not shown, hashed or held, on every system, and are read as they are when the script runs; a change to one after approval changes what runs and is not stopped. The approval page and terminal explain that the review covers the listed files and that the command can load or run other files as they exist at run time. Code and data cannot be told apart reliably (a data file can be `eval`ed, a module can be a config), so no distinction is made and nothing is scanned for. To have code covered, put it in the script.
  - **What the private copy protects against, and what it does not.** It protects against the original changing or being replaced after approval, against another user of the machine (the folder is owner-only), and against a copy that was altered before the start (found: nothing runs). The copy is checked again in the step that starts the program, by its path; the interpreter then opens it by its path, a moment later. **A process of the same user can still change the copy in that moment** (it owns the folder and can loosen its permissions), and no call available without a native helper or a privilege ties the check to the open. This is not claimed to be prevented: such a process can already read the program's environment, and so the secrets, from `/proc` (tested on Linux with `ptrace_scope=1`), so the approval is not a defence against code the person already runs as themselves. The original is never run in place of the copy; a copy that cannot be made or checked stops the run.
  - Startup files can still load. The allowed forms refuse `-l` and other options, but zsh always reads `~/.zshenv`, fish reads its config, Python loads its user site (`.pth` files, `usercustomize`), and similar files exist for other runtimes. An agent that can write to your profile or startup files can use them to run code the page never showed.
  - A script given to an interpreter must be text: binary scripts, zipapps and `.pyc` files are refused. Windows PowerShell 5.1 (`powershell`, not `pwsh`) refuses a script with non-ASCII bytes and no UTF-8 BOM, because it would read it in another code page than the page shows. A program that resolves to a Windows App Execution Alias (a zero-length reparse point in a `WindowsApps` folder, such as the `python3` stub, `winget` or `wt`) is refused with a message that names it; use the full path to the real program. A `.cmd` or `.bat` file (as the script of `cmd`, or run directly) must be ASCII: cmd reads it in the console code page, so a byte above 127 could mean another character than the page shows. A batch file run directly is started as `cmd.exe /d /c "path" args`, so the AutoRun commands of the registry are skipped.
  - Other startup code is not covered: a console code page that is a double-byte one (DBCS) can read ASCII-looking bytes in a `.ps1` or other script differently, and anything a profile or the registry runs outside the forms above. A renamed or copied interpreter skips the analysis; the `Run:` line still shows the real path and is what to check.
  - The environment denylist (the variables listed above) cannot be complete. Known gaps (the list is not complete): `PSModulePath`, `COMSPEC`, the effect of `PATH` and `PATHEXT` on programs the child starts, other `GIT_*` variables, and other runtime-specific `*OPT`/`*OPTS` variables.
  - The write lock: on Windows the files the page showed are opened so that nobody can write or delete them until the program ends, and are hashed once more after that (if that fails the run is refused). It covers only those files, not a renamed parent folder or a junction. Off Windows there is no lock: the files are only checked just before launch and an interpreter may read a file again after it was changed.
- **`.env` declarations are written by the agent.** The environment denylist cannot be complete, so an ordinary `.env` value (such as `GIT_CONFIG_COUNT`, `HTTPS_PROXY`, `SSL_CERT_FILE`, `CORECLR_PROFILER_PATH`, `GH_HOST`, and now also `NODE_OPTIONS` or `PYTHONSTARTUP`) can reach the program; that is why the page shows every ordinary value and warns first about the ones that change which code runs. Anything the page cannot show (an encrypted value, a secret) is never given to such a name. Anyone with the public key in the `.env` can write an `encrypted:` value, so the page shows a fingerprint of each ciphertext and warns about a file that is not the project's own. A value is shown only if it is on the page: a program that reads the `.env` (or `.env.local`) itself sees the whole file. The inherited environment of the `with-secrets` process is not shown, and an agent controls it too.
- **Redaction does not catch** reversed, split, compressed, or encrypted copies.
- **A program that sends its environment over the network is out of scope.**
- **No length limit on the command** except a technical one of 16,000 characters. The program refuses a longer command instead of cutting it short.
- **Only file symbolic links are shown.** A link in a parent folder (a junction, for example) is not.
- **A script can load other files.** The page shows, hashes and locks only the files named in the command (the script an interpreter runs, and a program that is a text script). Files that script loads are not shown, hashed or locked.
- **Same OS user.** A process that can read authority memory can recover secrets while the authority is unlocked. Signed state checks detect edited manifests, settings and secret rows. Grant seals detect modified grant rows. A process with file access can still delete the database or roll it back to an earlier valid copy.
- **The review key in memory.** While review is open, the private review key `R` is held in pinned memory and wiped when review closes, but each decryption uses it as a .NET base64url string (as with `K`), and the review text shown is a string too; neither can be wiped. A same-user process that reads the service's memory while review is open can read grant review text (command lines), never a secret value. Arguments in the audit trail stay in clear after masking (they are signed by the machine key, and a remote host has no `R`): a secret typed bare into an argument is not caught.
- **Sign counts are not signed.** They sit outside the manifest signature. An agent can set the admin keys' counts very high, and then every admin assertion fails ("sign count did not increase"). This is denial of service only: deleting `with-secrets.db` does the same.
- **The first passkey is trust on first use.** Whoever finishes the first-time setup becomes the first admin. Do it yourself, in your own terminal.
- **An agent that owns your terminal** can read the link and the confirmation code. Use a terminal the agent cannot read.
- **Plain `http` is not accepted for passkeys** except on localhost. Use `https` for any other name.
- **`.cmd` and `.bat` programs** run through `cmd.exe`, which reads quotes and `& | < > ^ % !` in arguments as commands. Arguments that contain them are refused.
- **A store from an earlier schema requires setup with schema version 4.** Keep a backup before removing an older database.
- **Passkeys that are not discoverable can no longer sign.** Approval sign-in lists the passkeys for `localhost`; make new passkeys discoverable.
- **Output is read as UTF-8.** Binary output and output in another code page (the console's OEM page, UTF-16) are garbled, and UTF-16 copies of a secret are not redacted.
