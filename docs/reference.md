# with-secrets reference

The detailed behaviour of every part, with the exact rules and limits. For what the tool is and how to start, read the [README](../README.md); for installing, enrolling machines, backup and recovery, read [operations](operations.md); for the design and threat model, read [architecture](architecture.md); for writing safe agent commands, read [agent usage](agent-usage.md).

## How approval works

1. The agent runs the command. The program checks the names against the store in `state.db` (and checks every stored ciphertext against its signed hash) and decrypts nothing.
2. It prints a **one-use link** to the terminal (stderr). The agent shows the link to you.
3. You open the link on any device that can reach it. The page shows the whole request: the program and the script as **full paths** (no `./`, no `..`), the secret names, the folder, and the agent's reason. The full path is also what runs. For the allowed forms the page shows the full command and the files it reads as code; the limits below remain. If the program or script is a symbolic link, the page adds a `Link:` line that shows where it leads. The page also shows what will run: an `Inline code:` block for code written in the command (`sh -c`, `cmd /c`, `pwsh -Command`, `python -c`, `node -e`, `perl -e`, `ruby -e`), and for every file that will be read as code (the script argument, and the program itself when it is a text file such as `evil.cmd`) its `Script file:` path, `Script SHA-256:` and a `Script contents:` block (first 200 lines, at most 16 KB; a binary or non-UTF-8 file says so). Every line of that code starts with `  | `, so no line of the agent's text can look like a line of the page (`Request id:`, `Run:`); control, bidi and zero-width characters are replaced by a mark; and these blocks are part of the text the passkey signs. A script that cannot be read, or is larger than 1 MB, refuses the run. The child gets no standard input (it reads end of file), and these variables are removed from its environment: `NODE_OPTIONS`, `BASH_ENV`, `ENV`, `PYTHONPATH`, `PYTHONSTARTUP`, `PYTHONHOME`, `PYTHONINSPECT`, `PERL5OPT`, `PERL5LIB`, `RUBYOPT`, `RUBYLIB`, `DOTNET_STARTUP_HOOKS`, `JAVA_TOOL_OPTIONS`, `_JAVA_OPTIONS`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `DYLD_INSERT_LIBRARIES`, `PERLLIB`, `ZDOTDIR`, `PYTHONUSERBASE`, `PYTHONWARNINGS`, `NODE_PATH`, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_EXEC_PATH`, `GIT_SSH_COMMAND`, `GIT_ASKPASS`, `SHELLOPTS`, `BASHOPTS`, `PS4`, `PS0`, `PROMPT_COMMAND`, and every name starting with `BASH_FUNC_`.
4. You read all of it, then press **Approve once** (or Ctrl+Enter, Cmd+Enter on a Mac). The approve controls stay off for a moment so they cannot be pressed by accident. Enter on the focused Deny button denies.
5. You prove it with a **passkey**. The passkey signs the request and the time you chose, so nothing can change the time afterwards. The program checks the proof itself, and accepts only a time the page offered. The page cannot approve anything alone. Sign-in lists all your passkeys for `localhost` (it does not name them), so it works with a password manager; new passkeys are created as discoverable keys.

While a passkey prompt is open, the button you tapped reads **Cancel**; if the prompt closes without an answer (it happens with some password managers on iPhone), tap it to abandon that attempt and tap the original button again.
6. If the proof is good, the program decrypts **only the named secrets** (with the Dotenvx crypto library), passes them to the program as environment variables, and redacts them from the output. Give a comma-separated list (`--secrets DB_URL,API_KEY`) to inject several secrets in one run, or declare them in the project's `.env` (see [Project `.env` declarations](#project-env-declarations)). There is no `--all`: every name must be written out.
7. It writes an audit line (names, command, result, and a hash of any script file in the command; never values).

Deny, a wrong proof, an error, or no answer before the time limit all deny the run (exit code 3); a run blocked on approval says which in its own sentence: "The user did not approve (denied on the page)" for Deny, "Nobody answered before the approval time limit" for a timeout (nothing ran; ask again), and the signed audit event records `user-denied` or `approval-timeout`. The link works once. A run needs the host service (exit code 6 when it is not running, exit code 7 when what answers is not this machine's service or no identity is pinned yet, exit code 8 when the authority is locked; see [The host service](#the-host-service) and [The authority lock and the admin web app](#the-authority-lock-and-the-admin-web-app)).

## First-time setup

Do steps 1 and 2 in **your own terminal** (an ssh session or a separate window), never in the agent's.

1. `with-secrets admin`. With nothing enrolled it is the first-time setup. Open the link, give the passkey a name in **Name for this passkey** (for example `laptop`; empty means `passkey`), then press **Step 1 of 2: create passkey** and create the passkey. A second button then appears: press **Step 2 of 2: confirm with your new passkey** and confirm with it (the new passkey signs the first state and itself as the first **admin** key). Each passkey prompt has its own tap, because iOS refuses a second prompt in the same tap. Then type the code the page shows into the terminal (only a code shown on the page you opened yourself; if it shows none, press Ctrl+C). Nothing is saved until you do: the settings and the passkey are written together, and so are the store's key pair and its vault (see below). The passkey works on the page's host, normally `localhost`. **The passkey must support PRF** (the WebAuthn extension that lets a passkey derive a secret): a passkey from your phone (iCloud Keychain, Google Password Manager) or a security key does, and one that does not is refused before anything is stored (`This passkey cannot do PRF (it cannot protect the secret store key). Use a passkey from your phone or a security key.`). The first passkey is trusted on first use, so make sure you are the one at the keyboard. It is an admin key: only admin keys can change the settings, the passkeys and the secrets. Add more passkeys later in the admin web app (**Passkeys**); a new one only approves runs unless you tick **Also make this key an admin** on its page. **We recommend two admin keys** (for example your laptop and your phone), so that a lost device does not lock you out (see [Admin keys](#admin-keys)). When the setup is done, the page and the terminal show the admin keys' fingerprints, such as `Admins: laptop ab12 cd34 ef56 7890`. **Write them down** (outside this machine). Every page the tool serves shows them again; check them each time you approve (see [Admin keys](#admin-keys)).
2. Store a secret in the admin web app (`with-secrets admin` prints its link): sign in with one passkey tap, open **Secrets**, type the name (`DB_URL`) and the value, and press **Save secret**; the tap signs the new state (one tap: the first secret is the same as any other, and needs no PRF). The terminal never sees the value. Nothing is asked in the terminal, and no key file is written. The secrets are stored in `%USERPROFILE%\.with-secrets\state.db` (see [The secret store](#the-secret-store)).
3. Give the agent the run command (see above) and tell it which secret names it may use.

## The authority lock and the admin web app

**The service starts LOCKED.** Until an administrator unlocks it, the authority and the host serve nothing secret-related: no run, no approve, no grant use (a grant never authorizes a run while locked), no check-in, no authority signature (the CNG authority signing key is not used, rotated or recovered), and no admin change that needs it. Locking also discards what the host held: the store key held for a grant is zeroed and dropped, the offline lease and the synchronized grants are cleared, grants end and launches that have not started are cancelled. `GET /v1/status` answers `{"protocolVersion":1,"running":true,"locked":true}` and nothing else. A run while locked prints one line and exits with **8**: `with-secrets: the authority is locked, so nothing was asked or run. Unlock it in the administration web app: http://localhost:8765/admin (one passkey tap; no sign-in is needed to unlock)`. The service prints the same link at start (it is public and carries nothing).

**There are no lock, unlock or other `admin` verbs.** `with-secrets admin` with nothing after it (only `--service-port N` and `--debug` are accepted) checks that the program on the port is this machine's host service (the same identity check as a run), prints the link of the authority's **admin web app** (`http://localhost:PORT/admin`, loopback only) and whether the service is running and locked, and, in a terminal on Windows, opens the link in your browser. It changes nothing and needs no passkey. Every administration function lives in the app.

### The admin web app

The administration is a **JSON API** on the service's own loopback port under `/api/v1` and the **administration web app** (React and TypeScript) uses it: the app is embedded in the exe and served at `/admin` on the same origin (any application route under `/admin` gets the app; a missing file or anything under `/api` never does). There is no server-rendered page. Every change is one fresh passkey tap that names the exact operation and its parameters; the browser session itself stays read-only. Without the app built into the exe, `/admin` answers the JSON 404 `web-application-not-built`. The API is described by an OpenAPI 3.1 document served at `/api/v1/openapi.json` (a copy is in `docs/api/openapi.json`; a test fails if they differ). Every answer carries `X-Api-Version: 1`; a request with another `X-Api-Version` is refused with a problem document listing the supported versions. Errors are RFC 9457 `application/problem+json` (a stable `code`, no secret, path or internals). Request bodies are small JSON (at most 4 KiB, validated against the schema, unknown or duplicate members refused). There is no CORS. Every machine function that used to be an `admin` verb is here:

- **Status** (`GET /api/v1/status`, public): running, locked or unlocked (and how), the **unlock mode**. `POST /api/v1/session` starts a sign-in; while locked, **unlock** is an operation.
- **Machines** (`/api/v1/machines`): fingerprint, status, security revision, host name and friendly name. Operations: `machine-approve` (with a friendly name; it pins the authority key for this machine), `machine-disable`, `machine-enable`, `machine-untrust`, `machine-trust` (the **full** 64-digit fingerprint is the confirmation), `machine-rename`, `machine-host-change`, and re-pin of the authority key.
- **Grants** (`/api/v1/grants`): list, `grant-extend`, `grant-renew`, `grant-revoke` (see [Grants](#grants)).
- **Audit** (`/api/v1/audit/events`, `/audit/changes`, `/audit/gaps`): the host events with filters for machine, project folder, time range, type, outcome, grant and text, a **gap view**, and the authority's own changes (see [Audit trail of the host service](#audit-trail-of-the-host-service)).
- **Settings** (`/api/v1/settings`): the audit retention, the admin **session timeouts**, the unlock mode (`policy-unattended` / `policy-manual`), and `authority-key-rotate` and `authority-key-recover`.
- **Passkeys** (`/api/v1/passkeys`): `passkey-enroll` and `passkey-unenroll`.

**Sessions.** One fresh passkey tap (an admin key, with user verification) on a one-use passkey page whose text names this sign-in starts a session. The browser that asked for it then claims it (`POST /api/v1/session/claim`, a POST by the same browser; `GET /api/v1/session` only reads and sets no cookie) and gets a random token in an `HttpOnly`, `SameSite=Strict` cookie scoped to `/api/v1` (its value bound to the service's port) **and a second, random secret in the answer to the claim, given once**. Every request must carry that secret in the `X-Admin-Token` header, reads included: the cookie alone is not a session. Browsers send cookies to every port of `localhost`, so a program served on another localhost port is sent the cookie; it does not have the secret, which the page keeps (in its tab's `sessionStorage`, per origin and port) and the service never shows again. The token is kept in the service's memory only (never in a file, a page, a log or the audit history). Before a session the browser has its own pre-session identity (`POST /api/v1/browser` makes the cookie and gives its secret once); a sign-in belongs to the browser that began it. A session ends after **15 minutes without use** and **8 hours after it started** (both settings, 1 to 120 and 1 to 1440 minutes), on **Sign out**, on **lock** and when the service **restarts**. A locked authority starts no session (only the unlock works without one). **A session only reads**: it is the right to see status, machines, grants, audit history and settings. It never authorizes a change.

**Every change is its own tap (authorize, tap, mutate).** 1. `POST /api/v1/authorizations` with the operation and its parameters (needs the session, its secret in `X-Admin-Token` and an exact `Origin`; the unlock and the lock need no session, only the browser identity and their own tap); the answer carries an authorization id and a one-use passkey page link. 2. A person taps an **admin passkey with user verification** on that page; its text names the operation and every parameter. 3. `GET /api/v1/authorizations/{id}` shows `pending`, `verified`, `refused`, `consumed` or `expired`. 4. The mutation endpoint (for example `POST /api/v1/machines/{fingerprint}/disable`) carries the authorization id. The service checks that the authorization is verified, was made for exactly this operation and these parameters, is at most 2 minutes old and unused, then spends it. A different operation or parameter burns it. A session, an old authorization, a reused one or one for another operation never satisfies a mutation (409 or 403). At most 32 are active and 30 start per minute. Passwords, proofs, codes and keys never appear in an answer.

**Audited.** The start of a session, and every attempt at a sensitive operation and its outcome (requested, refused, authorized, applied, failed), is written to the authority's audit history (no proof, token, code or key).

**Unlock mode.** Manual is the default: an administrator taps to unlock after each start. **Unattended unlock** is an explicit opt-in, changed only on the admin app by a fresh tap, reported at service start and on the app, and **weaker**: the service unlocks itself after it starts using 32 random bytes that the platform protects for this user (Windows DPAPI, current user; the sealed blob and a hash of the material are in the authority settings). Anything that can run as that user can open the same blob, so unattended unlock protects only against someone who cannot run as this user (for example a copied database). It only makes the service unlocked after a start: it never replaces the passkey tap for a sensitive operation and never creates or widens a grant. Any doubt (the blob will not open, the hash differs, no adapter) leaves the service locked. On a platform with no adapter (everything but Windows in this version) the option is refused with a clear message; no platform is assumed to have a protected store.

**Sensitive administrator operations** always need a fresh, single-use, time-limited passkey tap with user verification, bound to the operation and its parameters, with no fallback to a session, an unlock or unattended material: admin passkey enrollment, removal and replacement (in the app; `--recover` in a terminal), machine approve, disable, enable, untrust, trust, rename and host-name approval, grant extend, renew and revoke and the approval that creates a grant, secret changes (the Secrets page: each save and each removal is its own tap over the exact next state), settings (the page settings, the unlock policy, the session timeouts, the audit retention), the rotation of the secret store key, authority key rotation and recovery, and lock and unlock. Rotation and recovery of the authority key and every other change are refused while the authority is locked (and the refusal is audited). Each attempt and outcome is written to the authority's audit history (no proof, code or key). **Using** a valid grant is not administrative: it needs no further tap or approval (a store that needs the passkey taps once and the service holds the key for the grant's life, as described under [Grants](#grants)); unlocking creates no grant and widens none.

**Limits.** Locking is a gate in the service process, not a second layer of encryption: the authority signing key stays protected by the operating system and the lock decides when this process asks it to be used. Cookies are not isolated by port on `localhost`, so another program served on `localhost` in the same browser profile is sent the session cookie; the session only reads, every change needs its own tap and the anti-forgery value, so the cookie alone changes nothing. A local program can start a sign-in or an operation and ask you to tap: read the page text before you tap (it names the operation and says what it changes) and tap only for what you just chose. Adding or removing a passkey uses the existing enrollment pages (the new passkey's code is typed in the terminal that runs the service). The exit code **8** ("the authority is locked") can also be a child program's own exit code: the tool means "locked" only when it printed its one `with-secrets: the authority is locked ...` line on stderr (a locked authority never starts the child), so check that line, not the number alone. Zeroing is best effort (the runtime may have copied memory). The lock does not stop a program that already started. Malware running as your user can still read the user's files, drive your browser or wait for you to tap.

## Machine identity and the admin app


The host service has a **machine identity**: an ECDSA P-256 key made on first start (`with-secrets service`) and kept by Windows CNG as a non-exportable key, in the Platform Crypto Provider (TPM) when there is one and otherwise silently in the software provider. **On Linux (and WSL) the key is a file, not a CNG key**: ECDSA P-256 in `~/.with-secrets/keys/` (mode 0600, directory 0700). Before using it the program refuses, with one line that names the path and the fix (exit code 4): a link in place of the file or folder, a file or folder of another owner, a file group or other can access, a folder group or other can enter, or any folder up to the store folder that group or other can write (a sticky-bit folder is accepted); a new key is created exclusively and atomically; the service and `pair` are made non-dumpable and the key bytes and PRF output are `mlock`ed best effort (a refusal is one warning line in the log). That is **weaker than Windows CNG**: the file is an ordinary file, so anything running as that user (or root) can copy it, and a copy is the whole machine identity; there is no TPM, keyring or secret-service support. A container is a separate machine with its own identity and needs a persistent volume for `~/.with-secrets/keys`; see [docs/operations.md](operations.md) section 8 ("Linux host hardening": a dedicated service user or container, the key volume mounted only in the service container, the key folder out of backups). **Copied-identity warning:** when an authority sees a machine's connection replaced from a different address 3 times within 10 minutes (fixed), it writes a signed audit event and the Machines screen shows "This machine's identity may have been copied", with "Disable this machine if you did not start both."; nothing is disabled for you. Its **fingerprint** is the SHA-256 of the public key (shown as 16 groups of 4 hex digits). The service prints only the fingerprint and the host name. A separate **authority signing key** signs the authority's answers; its public key is pinned in `host.json` in the store folder (public data only) when this machine is first approved, and the host rejects an answer signed by any other key. The state of machines lives in `authority.db` in the store folder (separate from `state.db`; schema 5, schema 1 to 4 files are migrated in place (the first-cut audit tables of schema 4 are replaced); if it reports another schema, delete `authority.db` and enroll again).

**First run.** 1. Run `with-secrets service`; it enrolls this machine as **Pending**, starts **locked** and prints its fingerprint and the app's link. 2. Open the link the service printed (`with-secrets admin` prints it too; until this machine is approved nothing is pinned, so it marks the link "not verified", exits 0 and opens nothing), unlock with one passkey tap, sign in with another and open **Machines**. 3. Compare the fingerprint, type a friendly name and press **Approve**; a one-use page shows the action and the full fingerprint and you tap an **admin passkey**. This also pins the authority key in `host.json`. Until then every run is denied with one line naming the admin web app. 4. A run (the CLI) first asks the service to prove its identity (the fingerprint pinned in `host.json`); a program that merely holds the port cannot, and the run stops with exit code **7** before anything is sent. With nothing pinned yet the CLI prints the fingerprint the service claims and refuses until the app has approved and pinned it.

| Machine action (button) | What it does |
| --- | --- |
| **Approve** | Pending to Trusted, with a friendly name; pins the authority key for this machine |
| **Disable** / **Enable** | Trusted to Disabled (the revision goes up, grants end) / Disabled to Trusted (starts clean) |
| **Untrust** / **Trust again** | Withdraw trust (revision up) / trust again; **Trust again** needs the **full** 64-digit fingerprint typed as the confirmation |
| **Rename** | Change the friendly name (display only; revision unchanged) |
| **Approve host name change** | Accept the host name a Trusted machine started using; until then it is denied and the change is recorded |

Each change needs its own one-use page and an admin passkey tap; the page text, which the passkey signs, names the action, the machine's full fingerprint, host name, status and security revision, so a tap cannot be reused for another change. A non-admin key, no answer, a machine that changed meanwhile (the revision, or the host name that was shown) or a locked authority changes nothing. Only a **Trusted** machine is ever shown an approval or decrypts anything; Pending, Disabled and Untrusted machines are denied, nobody is asked, and nothing is decrypted.

**Authority key rotation and recovery.** A routine rotation is a signed transition (the new key signed by the current one); the host follows it by itself and moves its pin. If the authority key is lost or not trusted there is no transition: recovery is an explicit administrator action (**Recover** in the app's **Settings**) that makes a new key and pins it for this machine; other hosts must be enrolled again. **Rotate** is the routine rotation. Both need an admin passkey tap like every other change, and are refused while the authority is locked. A grant is honoured only under the machine's current security revision and never across a service restart. Limits: `host.json` can be written by any process of the same user, so this is no protection against a hostile same-user process; the CLI's identity check is not bound to the connection, so a relaying impostor on the port could still read the request it relays; CNG exists on Windows only, so `service` refuses elsewhere.

| `approve [--secrets A,B] --reason TEXT [-f FILE]... -- PROGRAM [ARGS...]` | Approve that exact request on the page and make a **grant** for it; nothing runs (see [Grants](#grants)) | Person, on the page |

| `admin` | With nothing enrolled, the first-time setup: it creates the first passkey (named on the page), the first admin key and the secret store's key pair (its public key and its private key wrapped under the master key into the **vault**, in the same signed first state; the private key is made in memory and stored nowhere else), with the default settings. Prints this machine's fingerprint and host name; the machine is Pending until an administrator approves it | Person, or a provisioning script |

## Secret names

A secret name is `NAME` or `folder/NAME`: one to four segments separated by a single `/`, at most 200 characters in all. The last segment is the name proper: letters, digits and underscores, starting with a letter, **in any case** (`STRIPE_KEY`, `stripe_key` and `Stripe_Key` are three different secrets), and not starting with `DOTENV_` (except `DOTENV_PRIVATE_KEY...`, the name a Dotenvx private key is stored under; see [Dotenvx encrypted values](#project-env-declarations)). Each folder segment is 1 to 64 of letters, digits, `_`, `.` and `-`, and is not `.` or `..`. So `STRIPE_KEY`, `team/STRIPE_KEY` and `team/payments/STRIPE_KEY` are names; `team//KEY`, `/KEY`, `KEY/`, `../KEY`, `a b/KEY`, `a?/KEY`, `a#/KEY`, `a%41/KEY`, `a\KEY`, `1KEY` and five or more segments are refused. The whole path is the store name, and it is data only: it is never a file path, and it is compared exactly (case counts, so `Team/KEY` and `team/KEY` are two secrets; the approval page shows the exact name). The Secrets page warns when a name differs from a stored name, or from another name of the same request, only by case, or only by look-alike characters (`l`, `I`, `1` and `O`, `0`); `--needs` adds `; differs only by case from: X` or `; looks like: X`. It is a warning, never a refusal. One rule is used everywhere: the Secrets page, the audit filters, `--needs`, `.env` references and the store. A folder has no meaning to the program; it only groups names (the Secrets page shows the whole path).

An environment variable cannot hold a `/`, so `--secrets` takes plain names only (the variable has the secret's name). A secret in a folder reaches a program through a `.env` reference: `STRIPE_KEY=secret://team/payments/STRIPE_KEY`.

## Project `.env` declarations

A project declares what it needs in its `.env` instead of the agent listing names. Example:

```
# .env in the project folder
LOG_LEVEL=Debug
STRIPE_KEY=secret://team/payments/STRIPE_PRODUCTION_KEY
GITHUB_TOKEN=secret://GITHUB_TOKEN
```

```
with-secrets --needs                                  # what would be asked for (names only)
with-secrets --reason "deploy" -- ./deploy.sh         # --secrets is no longer needed
with-secrets --secrets DB_URL --reason "deploy" -f .env -f ../shared.env -- ./deploy.sh
```

- **Files.** The default is `.env` in the working directory (no search upward). `-f`/`--env-file PATH` (repeatable) replaces that list. A missing default `.env` means no declarations; a missing `-f` file is an error (exit 2). A file over 1 MB is refused, and it must be a regular file (it is opened once and read to the cap); parsing stops at the first variable over 400 in one file. Limits, all errors (exit 2) and never cut: at most 16 files, 200 ordinary variables (encrypted ones count) and 200 pairs; a variable name of at most 128 characters; an ordinary value of at most 4096 characters. A `-f` file outside the working directory, or a symlink/junction, gets a `Link:` line on the page. The files are read once, when the request is built: the approval page, the fingerprint, the audit row and the launch all use that one reading, so a `.env` changed while the page is open changes nothing.
- **Syntax (Dotenvx style).** `NAME=value`, `#` comment lines, an optional `export `, blank lines, and values with single quotes (literal), double quotes (`\n`, `\r`, `\t`, `\"` and `\\` are escapes) or none (a ` #` ends the value). No `${}` expansion and no multiline values yet. A name is letters, digits and `_`, not starting with a digit. A bad line is an error that names the file and line (never the value). A name repeated in one file: the last line wins.
- **Three kinds of value, decided on the final value of each name.** `secret://...` is a reference; a value starting with `encrypted:` is a Dotenvx encrypted value (see **Dotenvx encrypted values** below; one that is overridden is ignored and asks for no key); anything else is an ordinary value.
- **Composition (like Dotenvx).** The first file wins per name. An existing environment variable beats an ordinary `.env` value (the program simply inherits it). A `secret://` reference always beats an inherited variable of the same name: it is explicit. A reference that loses to an earlier file's value is never requested, so only the final references reach the approval page and the store. `--secrets NAME` is a pair `NAME <- secret NAME`; the same variable given by `--secrets` and by a different reference is an error, and `--secrets` beats an ordinary `.env` value of that name.
- **Reference grammar.** `secret://NAME` or `secret://folder/NAME` (the rules of [Secret names](#secret-names)). The whole path is the store name: `secret://team/payments/STRIPE_KEY` is the secret `team/payments/STRIPE_KEY`. The left side is the variable the program receives, and may differ from the secret: `STRIPE_KEY=secret://team/payments/STRIPE_PRODUCTION_KEY`. Anything else (empty, `//`, a query, a fragment, a space, `%`, `..`, a name that starts with a digit) is an error that names the variable, not the value. At most 200 pairs per run.
- **The run.** The program gets every pair under its variable name, injected and redacted as before, and the ordinary values as plain environment variables (not secret, not redacted). `--reason` is always required. With neither `--secrets` nor a reference the error is the old one: "Name the secrets with --secrets NAME[,NAME...]".
- **The approval page and the passkey.** After the `Run:` line and the script blocks (so a long `.env` cannot push them out of sight) the page lists every `Env file:` path, then **one `Pair:` line per secret** (`Pair: STRIPE_KEY <- secret team/payments/STRIPE_PRODUCTION_KEY (renamed)`; `renamed` marks every pair whose variable differs from the secret's name; the `Secrets:` line still lists the store names), then one `decrypt with secret KEY: VARIABLE (cipher sha256 FINGERPRINT) from FILE` line per encrypted value (names and a 12-character fingerprint only), then **every ordinary variable with its value** (`  | LOG_LEVEL=Debug`, marked like script lines, control and bidi characters replaced by a mark). When an ordinary variable changes which code runs (a code-loading name such as `NODE_OPTIONS`, `PATH`, a proxy, a git identity), one **warning section** is shown on the page above the request text and above the Deny and Approve controls (heading "Warning: This run changes how the program loads code or where it sends data", every name with its visible value, a one-line reason per class: loads code, changes the library path, routes network traffic, changes git behaviour, and the sentence "Your approval covers exactly these values."); the same block is the `Warning:` line group in the text the passkey signs, and a remote authority shows the same section. These values are passed on to the program as written (not stripped, not refused) and are in the request fingerprint; a value the page cannot show (encrypted, or a secret reference) is still refused for such names. All of it is part of the text the passkey signs and of the request fingerprint (pairs, paths, names, values and the SHA-256 of every ciphertext). The terminal echo of the same page lists ordinary variable **names only**. The signed audit events keep names and fingerprints only (metadata: the secrets, the variable-to-secret pairs, the file paths, `decrypts` as `VARIABLE=KEY:FINGERPRINT`, never a value, a ciphertext or a key).
- **Trust: the agent can write the `.env`.** So the human approves the pairs, not the file. (1) Ordinary `.env` values that are on the code-loading list (`NODE_OPTIONS`, `PYTHONSTARTUP`...) are **passed on**: the page shows every ordinary value in full, except a value that looks like a credential (a name with PASSWORD, TOKEN, SECRET, API_KEY, PRIVATE_KEY, AUTH or CREDENTIAL in it, a password inside a URL or connection string, a bearer value, a known token shape), which it shows as `[hidden]`, and names the code-loading ones in a warning at the top of the block, and they are part of the fingerprint. The list under [How approval works](#how-approval-works) still strips what the agent's own shell supplies (the inherited environment). That list is not complete, so **the page is the control**: read the ordinary values it shows (a proxy, a CA file, a git or JVM option, an API base URL can redirect a secret or load code). (2) What the page cannot show is held to a stricter rule: a reference **or an encrypted value** whose variable is on that list, or is `PATH`, `PATHEXT`, `COMSPEC`, `SystemRoot`, `windir`, starts with `DOTENV_PRIVATE_KEY`, `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY`, `GIT_AUTHOR_` or `GIT_COMMITTER_`, or ends in `_PROXY` (case-insensitive), is refused (exit 2, before any page), and `--secrets NAME` is refused for such a name too. The rule is decided by the name alone (an environment variable of that name does not change it), the service applies it again to every request over the API, and a final filter applies it to the secrets before the child's environment is built.
- **Dotenvx encrypted values.** A value `NAME=encrypted:...` that is the final declaration is decrypted by the Dotenvx library (the same crypto as the store) with the private key held **in the secret store** under the Dotenvx name: `DOTENV_PRIVATE_KEY` for `.env` (and for any file not named `.env.suffix`), `DOTENV_PRIVATE_KEY_SUFFIX` for `.env.suffix` (the suffix in upper case, `-` and `.` become `_`; only ASCII letters, digits, `.`, `-`, `_` make a name). Store the key on the Secrets page under that name (`DOTENV_PRIVATE_KEY`). The key secret is part of the approval like any secret (it is on the `Secrets:` line), is read from the store only after the approval, is **never given to the program** (a reference, `--secrets` or a variable of that name is refused or left out), and is masked in the output if it ever appears there. The decrypted value is injected under the variable name and redacted from the output. It must be 6 to 4096 characters with no NUL, line break or other control character except a tab (a refusal is exit 2 naming the variable, with one message for every cause, so nothing tells a wrong key from a damaged value). An encrypted value that is overridden asks for no key. Because **anyone who has the public key (it sits in the `.env`) can write an `encrypted:` value**, the page shows a fingerprint of each ciphertext to compare with the committed file and warns when a value comes from a file that is not the project's own (a `.env` or `.env.NAME` directly in the working folder); the SHA-256 of every ciphertext is in the request fingerprint, so a grant does not cover a swapped ciphertext. Over the API the ciphertext travels in the request (`encrypted` member), the host service decrypts after the authority has approved and delivered the key secret like any other secret, so a remote authority works the same way. (3) Command grammar, script display and the file lock are unchanged. (4) The terminal shows names only. A reference to a secret you did not expect shows on the page as a pair: read it.
- **Not built yet.** `${VAR}` expansion, `--env NAME` layering, a project namespace, and the host service. `secret://project/NAME` is just a folder named `project` in the global store.

## The host service

The trusted side of a run is the **host service**: `with-secrets service [--port N]` runs it in the foreground (stop it with Ctrl+C). It listens on `127.0.0.1` and `[::1]` only, on port 8765 by default (`--port N`, or the `WITH_SECRETS_PORT` variable; there is no stored setting for it). A run is a client of it: the command line reads the `.env` files once, sends the request (names, pairs, reason, program, arguments, folder, the `.env` plan and the environment the program will inherit, with a digest over all of it) to `POST /v1/launch`, prints the approval link and the redacted output the service streams back, and ends with the exit code the service reports. The client never opens `state.db`, never decrypts and never starts the program; the service owns the approval page, the store, decryption, the program's environment, the launch, the redaction and the exit status. Reaching the API authorizes nothing by itself: no secret is opened until a passkey approved the page (or a grant that covers the exact request), and no response carries a secret. The API has no caller identity: **any local OS user (any process that can reach loopback) can reach it**, which is why a grant is not limited to one OS user: that is an open limit (see Known limits), not something this version enforces. The environment the program inherits is part of what is approved: the page shows how many variables there are and the names of those that change which code runs or where traffic goes (never values), and a different environment is a different approval. If the client is interrupted or disconnects after the program started, the service ends the program and its child processes; on Windows the program has a console of its own, so Ctrl+C in the service window does not reach it. At most 8 launches run at once. The API refuses a request whose `Host` is not a loopback name, that has an `Origin` header, is not JSON, is over 1 MB or slow, has an unknown field, a wrong digest or version, is expired, or reuses an id.

For a run: `--service-port N` (or `WITH_SECRETS_PORT`) picks the service's port. If the service is not running, the run prints `with-secrets: the host service is not running. Start it with: with-secrets service` and exits with **6**. Windows service installation and start at logon come later; the commands for a person (`--recover`, `--needs`) still open `state.db` themselves in this version.

## State and audit

Passkeys, the settings and the secrets are kept in `%USERPROFILE%\.with-secrets\state.db`, a SQLite database (WAL mode). The passkeys and the settings are one signed manifest (canonical JSON with a version that goes up with each change), signed by an admin passkey over `SHA-256(bind || SHA-256(manifest))`. The key that signed must be an admin key in that manifest. Every command verifies it first; if it fails (the file was edited outside the tool, a key or setting added, a signature swapped), every command stops with exit 4, `state failed verification: delete state.db to start over (only if you did not edit it)`, and nothing runs. Sign counts are kept beside it, outside the signature. A change is written only if the manifest is still the version the page started from, and only when it is signed by a key that is an admin key in the stored manifest (not one that the new manifest makes an admin) and stays one. **Verification only catches edits that keep your admin keys.** An agent that can write `state.db` can still delete it and write a whole new state signed by its own software key, with no page and no terminal. That state has other admin keys, so it shows **other fingerprints** on every page (see [Admin keys](#admin-keys)). (see [Approval reuse](#approval-reuse)). Every write is one transaction, so two runs at once cannot lose an update; a run waits up to 5 seconds for another one to finish writing. The database holds names and Dotenvx ciphertext, never secret values in plain text. A missing database is empty (nothing enrolled). A database that cannot be read, is damaged (checked with `PRAGMA integrity_check` at open), or stays locked longer than 5 seconds stops the command with exit 4; nothing is asked and nothing runs. If the audit entry cannot be written, nothing runs (exit 5).

There is no audit table in `state.db` and no hash chain. Every change to the store is an **administrative audit event**: a signed event of type `admin` (see [Audit trail](#audit-trail-of-the-host-service)) whose outcome is the event name (`secrets-set`, `secrets-removed`, `settings-changed`, `setup`, `key-enrolled`, `key-removed`, `key-rotated`, `approvals-revoked`, `recovered`, and `change-denied` for a refused or failed change with the command, the secret names and why), whose reason is a short text with the approving admin key's name (`key-enrolled` says whether the new key is an admin; `approvals-revoked` says how many were cleared), and whose arguments are names only (secret, setting or key names). It holds names, never values. The event is signed with the machine identity key and committed to the outbox (`audit-outbox.db`) inside the change's own `state.db` write transaction, just before it commits: if the event cannot be committed, the change is not made. (If `state.db` then fails to commit, a record of a change that did not happen can remain; the reverse, a change without a record, cannot.) A refused change is recorded only when `state.db` already exists. The service sends these events to the authority with the run events; you read them in the admin web app. The old `--audit` command and its log are gone.

The schema version is 11 (the signed manifest, with any number of admin keys, holds the passkeys with their key slots, the settings, the store's public key, the vault, the recovery slot and the hash of every secret; the `secrets` table holds one Dotenvx ciphertext per secret). A database of another schema version (an older or newer one) is never moved forward: the command stops with exit 4 and says to delete `state.db` to start over. There is no import from the `.env.local` file of earlier versions. **An existing `state.db` (schema 8 or older) is incompatible with the recovery slot: delete it and set up again** (`with-secrets admin`; the store key is made there, then store the secrets in the admin web app); there is no migration. The program reads no other file in the store folder.

### The secret store

- **Rows.** Each secret is one row of the `secrets` table in `state.db`: its name and its value encrypted by Dotenvx (the `encrypted:` format, ECIES on secp256k1). Dotenvx is the crypto library here, not the file store: there is no `.env.local` and no `.env.keys`.
- **Signed hashes.** Anyone with the public key can make a valid ciphertext, so a row alone proves nothing. The signed manifest therefore holds the store's public key and, for every secret, the SHA-256 of its ciphertext. Every read (the list of names, a run, a secret change) checks every row against its hash first. A row whose ciphertext is not the signed one (another valid ciphertext, or another row's), a row without a hash and a hash without a row all stop the command with exit 4 (`the secret store failed verification`), before anything is asked or decrypted. A changed hash or store key in the manifest fails the manifest's own signature, so every command stops.
- **One tap to store a secret.** As you type, the Secrets page sends the encrypted values to the program, which checks them, encrypts each to the store key and answers with the next manifest (names and hashes, nothing secret). Your Save tap then signs `SHA-256(bind || SHA-256(ct) || SHA-256(manifest))` once: it covers both the values the page sent and the hashes of the rows the program will write. The rows, the new manifest and the audit entry are one transaction that is written only if the state is still the version the page started from.
- **Removing a secret** asks you to sign the next manifest, without the removed hashes; the rows go in the same transaction.
- **Only the requested rows are decrypted**, with the private key passed as a parameter (never an environment variable or a file). A run with `--secrets A` decrypts `A` and no other secret.
- **The store key never rests on the machine.** The Dotenvx private key `K` exists only wrapped, and in memory during an approved run. Each enrolled passkey has a **key slot** in the signed manifest (`salt`, `wrap`): the passkey's WebAuthn PRF output for that salt gives a key-encryption key (HKDF-SHA-256), which unwraps a random **master key** `MK` (AES-256-GCM, bound to the credential id and the salt); `MK` unwraps the **vault**, which is `K` encrypted with AES-256-GCM under `MK` (bound to the store's public key). The vault and the slots are in the signed manifest, so an edited slot or vault fails verification (exit 4). Only a passkey with PRF can be enrolled. Every slot in a store uses the same `salt` (the first key's; adding a passkey reuses it), because the sign-in page can pass only one `eval` salt; the PRF output, and so the key-encryption key, still differs per passkey. On iPhone, use a passkey in Chrome; Safari did not return PRF output at sign-in in our test.
- **A run needs one tap that does two things.** The approval page asks the passkey for its assertion and its PRF output in the same prompt. The browser encrypts the PRF output to a key that exists only for that page in the program (ECDH P-256, HKDF-SHA-256, AES-256-GCM, bound to the page), sends it with the proof, and the program derives `K` only after the proof verifies, decrypts only the requested rows, and zeroes `K`, `MK`, the key-encryption key and the PRF output. A missing, garbled or foreign PRF payload denies the run; there is no fallback. The same holds when a key is enrolled (the approving admin passkey releases `MK` for the new key's slot). The first-time setup makes the master key `MK`, the store key pair and the vault in memory, all in the first signed manifest, and then zeroes them, so storing a secret never needs the master key.
- **Every run asks.** The key to the values is released by the approving passkey (PRF) at every run, so nothing an approval says is kept for a later run. A pre-approval (a grant, made in the administration web app) is the way to let one exact command run again without asking.
- **Cross-platform.** There is no Credential Manager, no `.env.keys` and no Windows-only step: the store works wherever the tool runs and a PRF passkey is available.
- **A failed or abandoned first-time setup leaves no key anywhere.** The store's private key is made in memory at the first-time setup and goes only into the vault of the first manifest the new admin passkey signs, which is written in one transaction with the settings and the key. A cancelled or failed first-time setup stores nothing; storing a secret stores only ciphertexts and their hashes.
- **Memory.** Decrypted values are kept as bytes and zeroed when the program ends. `K`, `MK`, the key-encryption key and the PRF output are byte arrays that are zeroed after use, and during a call they are in the process's memory. Some copies cannot be wiped: the string Dotenvx's decrypt returns, the strings the redactor and the child's environment need, the child's environment block itself, and the private key as a hex string (a .NET string). .NET strings stay in memory until the garbage collector reuses it. An agent running as the same user could read the process's memory while a run is open. **If `K` is read from memory once, all secrets present and future are exposed until the keys are rotated (Settings, **Secret store key**) or the store is rebuilt with `--recover`.** The same holds for a tap on a look-alike approval page served by another local process on localhost (a passkey's RP ID ignores ports, so the passkey cannot tell the pages apart): that tap releases `MK` and so `K`. Check the link the terminal printed before you tap.
- **Removing a passkey does not stop it from opening `MK` using an older copy of `state.db`.** `MK` and `K` are not rotated when a passkey is removed; the rotation of the secret store key rotates them (and keeps only the tapped key). Until you rotate, a removed key with its authenticator, plus an older `state.db` copy that still has its slot and the vault, still opens the store key.
- **The PRF output crosses localhost HTTP encrypted** to the page's own server key. This protects against passive observation, for example in a tunnel that ends TLS; it does not protect against an active man in the middle who replaces the page's server key (the same limit as the secret values).

### One link per command

A command prints one link. When it has more steps (`--recover`; in the admin app, adding a passkey and the rotation of the secret store key), the page of a step that has verified (the passkey proof or the recovery code was checked) answers with the address of the next step's page, made at that moment (a new one-use token, the same server and port; the host is the admin keys' host or the `baseUrl` host, as before), and moves on by itself with the text "Step done. Continuing..." If the browser blocks that, the page shows the same address as a link and a **Continue** button. The next page needs the step before it done: its address is not known before, and each page works once. Every page keeps its own rules (a passkey prompt only in a tap, Cancel, retries, diagnostics). The command's time limit is shared by its steps, not restarted at each. Where a command ends with a code from the page (the first-time setup, adding a passkey, the new-store step of `--recover`), the terminal asks for it after every tap, and nothing is stored before it is typed. While it waits, the last thing on the terminal is `Waiting for the code from the page. Paste it here and press Enter: ` with the cursor after it; the command writes nothing else meanwhile (no line is held back or dropped; with `--debug` the diagnostic lines print as they arrive). The first-time setup is one page too (its Step 2 button signs the new state on the same page), like removing a passkey.

If the reply of a step that verified is lost on the way, the page sends the same request again and gets the same reply (the same next address or the same code), which makes no second page and no second code; the program keeps that reply only in memory until the command ends, and a different request after the decision gets 404. If the page still did not move on, press Ctrl+C and run the command again. A page whose step is gone says so in a short text (404) and points to the terminal.

### The recovery code

- **The first-time setup shows a recovery code, once.** It is 8 groups of 4 letters and digits (for example `ABCD-EFGH-JKLM-NPQR-STUV-WXYZ-2345-6723`), shown on the last page together with the 6-digit code, in the page only (never in the terminal, a log, the audit log or `state.db`). **Write it down and keep it offline**, apart from this computer. **Anyone who has the code and `state.db` can open all your secrets**, so keep it as private as a password. Typing it accepts lower case, spaces and dashes.
- **What it is.** 20 random bytes. `RK = HKDF-SHA-256(code, salt, "with-secrets/v1 recovery")` opens the **recovery slot** in the signed manifest: `MK` wrapped with AES-256-GCM under `RK` (12-byte nonce, the store public key as associated data). `MK` then opens the vault, like a passkey's slot does.
- **`with-secrets --recover`** is for when every passkey is lost. Page 1 (the only link the terminal prints) asks for the code (the browser encrypts it to a key that exists only for that page, like a secret value; three wrong codes end it, and a refusal changes nothing). The page then moves on by itself (see [One link per command](#one-link-per-command)) to a first setup on a new, empty state: you create a **new passkey** (and can change the settings), and the new master key, store key, vault and **recovery code** are made. The secrets are decrypted with the old store key and encrypted again for the new one, one at a time, and everything is written in one transaction. Only then is the old file renamed to `state.db.recovered-<UTC yyyyMMddHHmmss>` (never deleted) and the new one put in place, with a `recovered` audit entry (the number of secrets and the old file name). **The old admin keys are gone** from the new state; add them again as passkeys in the admin web app. Any failure leaves the old `state.db` as it was. It works while the old keys still exist, too. The old recovery code does not open the new store.
- **Rotating the secret store key** (admin web app, Settings, **Secret store key**) makes a new store key `K` and master key `MK` and encrypts every secret again. Tap 1 is an admin approval that also releases the PRF output of the key you tap (the page lists the keys that will be removed); tap 2 (**Step 2 of 2**, reached from the page after tap 1; the terminal prints no second link) has the same key sign the new state, including the hashes of the new ciphertexts. **Only the key you tap stays**: every other key is removed, because their slots wrap the old `MK` and would still open an older copy of `state.db`. Add them again as passkeys. A new recovery code is shown once on the last page and the old one stops working. The change is one transaction (with a `key-rotated` audit entry naming the removed keys); a failure or a timeout between the taps changes nothing. A key that has a slot is required.
- **Compare the fingerprint before you type the code.** `--recover` and the rotation of the secret store key print the old store's admin fingerprint line (`Admins: laptop ab12 cd34 ef56 7890`, the same as on every page) in the terminal of the command, or of the service for the rotation, before the link, and tell you to compare it with the one you wrote down. If it differs, do not type the code or approve: the state was replaced. Why: a typed recovery code is not tied to the page's origin the way a passkey tap is, so a look-alike page can read it; only the fingerprint, checked against your own note, tells you the page belongs to your store.
- **Rotation does not help if the kept key's PRF output may have leaked** (a tap on a look-alike page, a memory read during a run): the leaked output still opens the new master key, because the kept key keeps its slot salt. After such a doubt, tap a key that was never used on a doubtful page, or rebuild the store with `--recover` on new keys.
- **Show-once.** The new recovery code is shown on the last page only once. If the page did not show it (lost connection), the old code is already dead after the rotation: rotate again. After the first-time setup or `--recover`, rotate to get a new code.
- **Rotating does not recall values that were already exposed.** An older copy of `state.db` plus an old key, or an old recovery code, still opens the secrets it held. Rotate the secrets themselves at their source (the service that issued them) as well.
- **Schema 9.** The recovery slot is new in schema 9. A `state.db` of schema 8 or older is not moved forward: delete it and set up again (`with-secrets admin`), then store the secrets again in the admin web app. There is no migration.

## Admin keys

Any number of passkeys can be **admin keys**; at least one always is. The first passkey (from the first-time setup) is an admin key. A passkey added in the admin web app becomes one only when you tick **Also make this key an admin** on its page; that choice is part of the new state the approving admin key signs, and the page says it. Only admin keys can change the settings, the passkeys and the secrets; every passkey can approve runs. Each page that changes the state offers all admin keys that work at its host.

- **Use two admin keys**, for example your laptop and your phone. Then a lost or broken device is no emergency: the other admin key removes it on the **Passkeys** page of the admin web app.
- **To replace an admin key** (a new device): add the new key on the **Passkeys** page, tick **Also make this key an admin**, then remove the old one there, approved with the new key (an admin key cannot approve its own removal).
- **After a reset, delete the old `localhost` passkeys in your password manager.** Each passkey is labelled `with-secrets <name> <random guid>` (the name is cut first if the label would pass 64 characters); the label is only for display.
- **The last admin key cannot be removed.** With a single admin key and that device lost, nothing can change the state any more: delete `state.db` and run `with-secrets admin` again (your passkeys, settings and secrets start over: the secrets are in `state.db` too, so store them again in the admin web app).

### The fingerprints

An admin key's fingerprint is the first 8 bytes of SHA-256 of its public key (as stored in the manifest), written as four groups of four hex digits. Every admin key is listed, oldest first: `Admins: laptop ab12 cd34 ef56 7890, phone 1234 5678 9abc def0`. It is not secret. The line is shown:

- on every page the tool serves: run approvals, adding and removing passkeys, secret changes and the rotation of the secret store key (on an approval page it is part of the text your passkey signs);
- once when the first-time setup finishes, and when adding a passkey shows its code, on the page and in the terminal.

Note the fingerprints down when you first see them, and check the line on each page before you approve. **If it ever changes without you adding or removing an admin key, the state was replaced**: someone deleted `state.db` and set up their own admin key, or an admin key was added that you did not add. Do not approve anything; find out what happened, then delete `state.db` and set up again with `with-secrets admin`. The fingerprints do not stop a same-user agent from resetting the database; they make the reset visible to you. Restoring an older copy of `state.db` (with your own admin keys) is not detected: it can bring back passkeys you removed (an admin key you removed too) and settings you changed, and old secret values, including one you replaced after it leaked (so rotate a leaked value at its source, not only here). Nothing recalls a secret a program already saw: rotate any value that may have leaked.

## Where the page can be reached

By default the page is at `http://localhost:<port>` on the machine that runs the program, with a free port picked each time. When that machine is remote, forward the port with ssh and open the link on your own computer:

```
ssh -L PORT:localhost:PORT user@host
```

Set `port` in the admin web app to a fixed number so the forward can be set up once. For one call, `--port N` (1 to 65535) does the same without changing the setting: `with-secrets --recover --port 8765`, then `ssh -L 8765:localhost:8765 user@host`. It is not saved, and if the port is in use the call fails (no other port is tried). To use an HTTPS name (a Cloudflare or Tailscale name, for example), set `baseUrl` and `port`, and point that name at the port. Browsers allow passkeys only on `https` or `localhost`, so plain `http` to another name does not work. A passkey is tied to the host name it was created for. Changing `baseUrl` removes no passkey: a passkey made for `localhost` keeps working on the localhost page (a run picks it by itself). Add a passkey for the new name on the **Passkeys** page of the admin web app (it is approved with a passkey you already have).

## Settings

The settings are kept in `state.db` in the protected folder, not in an environment variable or flag, because the agent controls those. They change only in the admin web app (**Settings**, **Approval pages**):

- **Save** is approved with your admin passkey, which signs exactly the new state: the challenge is `SHA-256(bind || SHA-256(manifest))`, the manifest being the current one with the new values and the next version. The program checks the passkey, then writes the new manifest and an audit entry (the names of the settings that changed, old -> new, and the key; none of the settings is secret) in one transaction. A state that changed meanwhile, a wrong proof or a value out of its limits changes nothing.
- The first-time setup (`with-secrets admin` with nothing enrolled) uses the defaults. There is no way to save settings without a passkey.

With nothing enrolled every setting has its default. A manifest with a value that cannot be used never verifies, so it stops every command with exit 4.

| Setting | Default | Meaning and limits |
| --- | --- | --- |
| `reuseMaxMinutes` | `480` | The ceiling: the longest time a grant may last. 10 to 1440. Longer times are not offered, and a grant longer than the current ceiling is not honoured |
| `baseUrl` | none | The address of the page, such as `https://secrets.example.net`. Empty for none. A full `http` or `https` address, no user name or password, at most 2048 characters |
| `port` | `0` | The port the page listens on. 0 picks a free one. 0 to 65535. `--port N` overrides it for one call |
| `timeoutMinutes` | `5` | How long the program waits for an answer on a page. 1 to 30 |

## Approval reuse

**There is none for a run: every run asks, and the approval page offers only Approve once.** A saved approval would have no passkey tap and so no PRF output to open the store key. (Earlier versions kept the code for it; it has been removed.) To let one exact command run again without asking, make a pre-approval (a grant): `with-secrets approve ...` shows it in the Approvals page of the administration web app, where you pick the time (up to `reuseMaxMinutes`) and tap once. The time is signed with the passkey: `SHA-256(bind || "reuse=" || minutes)`. Grants are listed, extended and revoked on the Grants page.

## Rules

- **Terminal output is public.** The agent reads it. Nothing the program prints is secret: it shows links, names, and results, never values or key bytes.
- Run `with-secrets admin` (first-time setup) and `--recover` only in a terminal you own. Values are typed in the browser, never in a terminal. The confirmation code of a new passkey is shown only on the page (the last page of the command) and typed by you in that terminal.
- **Only type a confirmation code that a page you opened yourself shows.** If the page has already ended or shows no code, press Ctrl+C. (An agent that holds the link could register its own key and pass you its code.)

## Logging

Normally the terminal shows only what a command always showed: its result, errors, links and the code prompt. The lines that explain what the program is doing (`with-secrets: connection opened (3 s)`, `request POST /proof (headers read, 3 s)`, `proof received (N bytes)`, `proof checked: accepted`) are Debug events and are not shown.

- **`--debug`** (with any command, before `--`) or **`WITH_SECRETS_DEBUG=1`**: those lines print on the terminal as they happen, and are also written to the log file.
- **Log file:** `%USERPROFILE%\.with-secrets\logs\with-secrets-YYYYMMDD.log`, one file a day, rolled at 1 MB, the newest 7 files kept. The folder is made when needed; if the file cannot be opened or written, the command goes on without it.
- **Always in the file, without `--debug`:** warnings and errors: a request handler that failed (the exception type name only), a request body that timed out, a state that failed its check, an audit row that could not be written.
- **Nothing secret:** the log holds route words (`page`, `proof`, `save`...), sizes, whole seconds and exception type names. Never a link or token, a request body, a key, PRF output, a code or recovery code, a secret value, a `.env` value or exception text.

## Troubleshooting

If a page sits on "Checking your passkey..." and then says the program did not answer, run the command again with `--debug` (or set `WITH_SECRETS_DEBUG=1`) and look at the terminal and the log file (see [Logging](#logging)). `with-secrets: connection opened (N s)` and `request POST /proof (headers read, N s)` (a method, a route word and whole seconds since the link was made, never the link, a body or a key) show that the request reached the program; `body slow` means its body was still arriving after 5 seconds; no line means it never arrived. The page adds a `Diagnostics:` line after a failed post (never after a success), with times only: when it was opened, when the passkey prompt started and answered, how long the page was hidden, each attempt, and whether the phone was online. Send those lines, not a screenshot of anything secret, when you report a problem.

## Grants

`with-secrets approve --secrets NAME[,NAME...] --reason TEXT -- PROGRAM [ARGS...]` takes the same arguments as a run, shows the same approval page, and on **Approve** makes a **grant** for that exact request instead of running it (nothing is decrypted, nothing starts). The page offers the times the reuse setting allows (10 minutes up to 24 hours; the approval-reuse setting must be on). A later `run` of a request in the same scope (the same arguments, secret names and pairs, resolved program, working folder, script contents and inherited environment, and the same machine) is covered by the grant: no approval page decision is needed, and the run says so in one line. Anything else (another program or secret, an edited script, an ended or revoked grant) goes through the normal page. A grant has its own scope key (machine, request fingerprint and the **full argument list**, so `python -c ...`, `bash -c ...` or `node -e ...` inline code is part of it): a grant for one command line never covers another. The approve page is headed as creating a grant, says that no program runs, and what it covers.

The store key still has to come from somewhere. The first run under a grant gets it from one passkey tap on the page (as every run did before); the service then holds that key in memory **for the grant** and later runs under it need no tap. It is dropped and zeroed when the grant ends or is revoked, the machine is disabled or untrusted, the security revision changes, the authority stops vouching for the machine, the link to a remote authority fails, the service restarts, or a run fails. It is never written to disk or a log. The page of the tap that starts holding the key says so plainly (the service keeps the key, which opens all your secrets, until the grant's end, or until restart for a grant with no end), and the held key is bound to that grant, scope, revision and end at the tap. It is held in pinned memory the collector does not move, so it can be zeroed. This is a deliberate trade-off; a cleaner mitigation is an open item.

In the admin web app, the **Grants** view (`GET /api/v1/grants`, signed in) lists each grant: id, state, end, machine, secret names, program and folder (never the scope key). Its buttons start **Extend** (move the end of an active grant later, N minutes from its present end, 1 to 1440, or give it no end), **Renew** (give an ended grant a new end, counted from now) and **Revoke** (end the grant now; a connected host is told at once and cancels launches that have not started). Each one opens its own one-use passkey page and needs an admin passkey tap with user verification; a grant that changed while the page was open is refused. The old `admin grant ...` commands no longer exist. None of the three changes the machine's security revision. A grant with no end is possible only through Extend or Renew with "no end".

**A host whose authority cannot be reached fails closed.** There is no offline lease and no offline use of a grant. Every run asks the authority (a grant is checked with it on every run); when the authority cannot be reached, or does not vouch for the machine, nothing is decrypted and nothing runs, whatever the host synchronized earlier, and the held key is dropped and zeroed when the link to a remote authority fails. The host is vouched for only while its last verified check-in with the authority said the machine is Trusted and its host name is the bound one; that state lives in memory only, a restart destroys it, a changed or replayed check-in answer vouches for nothing, and changing the system date does not matter. A host makes no new approval, extension or renewal while the authority cannot be reached. A connected host applies a revocation or a disable at once. After a restart the service checks in with its authority before it accepts a request (it answers 503 until then, which a run reports as exit **9**: ask again in a moment).

A grant row is backed by the person's passkey assertion over the page text (scope, security revision, minutes), stored with the row and verified against the signed manifest at every use; an extension, renewal or revocation is backed by an admin assertion over the exact change. A row without valid evidence (planted, edited, moved to another grant) is ignored. Limits: a process of the same OS user can still roll back a whole `authority.db` to an older copy, or delete rows; it cannot create or lengthen a grant. The local API has no caller identity, so a grant is not limited to one OS user (a same-user check is planned). A revocation cancels every launch that has not started, not only those under that grant.

## Audit trail of the host service

The host service keeps a **signed audit trail**; it is the only audit log. Besides every run it does, it holds the administrative events of the human commands and the admin app (see "Administrative events" below). Each run produces separate events: the **authorization** decision (approved on the page, covered by a grant, or denied with a reason code), the **launch** outcome (started, or why not) and the **execution** outcome (the exit code). An event has a unique id, a per-machine sequence number (1, 2, 3, ... with no gaps), a time, the machine fingerprint, the working folder, the program, the arguments, the grant id when a grant was used, and a signature by the machine identity key. It never holds an OS user name, a secret value or an environment value; arguments are recorded with values that look like secrets masked (a value after `--token`, `password=`, `Authorization: Bearer`, the password of a URL), and anything very long is cut (a folder or program path over 4096 characters is cut host-side, with a marker, so the authority never refuses the event of a run that went ahead).

The authorization event is committed to the host's own outbox, `audit-outbox.db` in the store folder (SQLite, WAL, synced to disk), **before** a run decrypts anything. If it cannot be committed (the disk is full or the file is damaged), the run does not happen: exit **5**. The launch and execution events come after the fact, so a failure to record them is only logged. The service sends the outbox to the authority by itself and keeps retrying until the authority has stored the events and signed an acknowledgement; only then are they removed locally, and a launch never waits for the upload. The authority checks each machine signature, stores each event id once, notes any hole or reused number in a machine's sequence (it never refuses an event for that) and keeps events for its retention (365 days unless the authority is told otherwise; 0 keeps everything). There is no hash chain and no export.

**Administrative events.** A change to the secret store, the passkeys, the settings or the store itself (also a refused one) is an event of type `admin`: its outcome is the event name, its reason carries the approving key's name, and its arguments are the secret, setting or key names; never a value, a code or key material. Every event can also carry a small signed **metadata** object (names and fingerprints only): a run's authorization event lists the secret names, the variable mapping, the `.env` files, the file fingerprints, the approving key and the reuse minutes; an administrative event lists the full detail, the key and the names. The admin app shows it as read-only text. It is signed, numbered, committed and uploaded exactly as a run's events are (the commands write it to the same outbox with the machine identity key, and the service uploads it; if no service runs, it waits in the outbox). Filter by type `admin` in the admin web app.

The history is read in the **admin web app** (`/api/v1/audit/events`, signed in; the `admin audit` command no longer exists). Filters: machine (fingerprint start), project (working directory), time range (since, until), type (authorization, launch, execution or admin), authorization or launch/execution outcome, grant id, text, and how many (1 to 1000); a **gap view** lists the holes. It is read-only. If `audit-outbox.db` reports another schema or is damaged, delete it to start over (the numbering then restarts at 1 under a new epoch id, which the authority records as an "epoch" gap; the holes an earlier epoch left stay open). Limit: a process of the same OS user can still delete the outbox or tamper with `authority.db`; the trail does not prove that a compromised host reported truthfully.

## Remote authority over mutual TLS

A host service can use a **remote authority** instead of the local one, with no change to the CLI or the local API. The host connects **directly** to its one configured authority over HTTPS: **TLS 1.3 with a certificate on both sides, and HTTP/2**. There is no relay, no custom handshake and no application-level encryption (the TLS channel is the encryption); TLS 1.2, HTTP/1.1, plain HTTP, session resumption and 0-RTT are not offered, and a client that cannot do TLS 1.3 gets no connection. `host.json` (public data only) selects it and keeps the address and the authority's identity apart:

```json
"remote": { "endpoint": "https://127.0.0.1:8790", "authorityIdentityFingerprint": "<64 hex digits>", "authorityIdentityCertificate": "<base64 DER>" }
```

The address is routing information only. **Who the authority is** is its identity certificate: every machine has one persistent self-signed identity certificate (`machine-identity.cer` beside `host.json`, made from the machine's CNG identity key, ECDSA P-256, ten years, a CA with path length 0 per architecture 10.2, key usage DigitalSignature and KeyCertSign). A running instance also makes a **temporary certificate**: a fresh in-memory TLS key and a 24-hour leaf signed by the identity key (SAN `urn:with-secrets:machine:<fingerprint>`, serverAuth and clientAuth), replaced an hour before it expires; the same certificate is the authority's server certificate and a host's client certificate. Each side validates the other only against the one enrolled or configured identity certificate (signature, dates, not a CA, key usage, both purposes, the machine named in the SAN); the operating system's trust store and the host name in the address are not consulted. On Windows the in-memory TLS key is a named, non-exportable CNG key that is deleted when the process ends, because the Windows TLS stack (SChannel) cannot use an ephemeral key; a process that is killed leaves such a key behind in the user's key store (harmless: it is a private key nobody can use again, and no certificate is trusted because of it).

The authority listens on **its own port, separate from the loopback browser and client APIs**: `with-secrets service --machine-port 8790` (loopback by default; `--machine-bind ADDRESS` names one other address; 0.0.0.0 and `[::]` are refused). A service started before the authority has a signing key (it is made by the first approval) has no machine listener yet and starts it by itself as soon as that approval makes the key: no restart, the same address, the same rules about who may connect. Every route needs the client certificate and the machine's identity comes only from it, never from a header or a field; a machine that is not Trusted now (Pending, Disabled, Untrusted) is refused on every route and its connections get GOAWAY and are closed after a short grace; a locked authority serves nothing. A machine whose certificate is well formed but not enrolled can reach **only the pairing route**, which serves the one-time invitation protocol (see Pairing in docs/operations.md). Answers carry `Cache-Control: no-store`, are never compressed, are UTF-8 `application/json` only, and errors are a short code with a correlation id and nothing else; request size, concurrent requests and time are bounded and excess is refused rather than queued. The host follows no redirect, uses no proxy, has no fallback and backs off exponentially with jitter. A request is retried under the same id (the authority answers once); **a secret release whose answer is lost is never retried**.

Invalidations and grant events keep their sequencing, acknowledgements and revision rules, carried by an HTTP/2 **long poll** (one outstanding poll per host; no heartbeat, no periodic empty polling). On every reconnect the host authenticates, checks status and revision and purges what it holds if the revision differs. The signatures on authority-issued records and machine-signed audit events are unchanged. A host that has no authority signing key pinned asks the authority for it over the identity-pinned connection once the authority trusts the host, and pins it in `host.json`.

A host is introduced to its authority by **pairing**: `with-secrets pair` (see [Pairing a machine](#pairing-a-machine)). The old `--authority-fingerprint`, `--machine-cert` and `relay` command and the reserved `admin https://AUTHORITY` form are gone.

### Pairing a machine

A machine joins an authority with a **one-time invitation** that the administrator creates in the authority's admin web app. Nothing is typed into a URL, an argument or a request: the invitation is a credential bundle (`wsp1;https://HOST:8790;ID;CODE`: the authority's address, a unique identifier and a 128-bit random code) shown **once** and never stored in readable form.

1. **Administrator, on the authority.** Admin app, **Machines**, **Add a machine**, **Continue to passkey** (the passkey page opens by itself). The passkey page names the authority address and says the invitation is valid 10 minutes (fixed, not configurable) and registers one machine. After the tap the bundle is shown once in that dialog; copy it (if the page was closed before it was collected, it is held for 5 minutes and then lost: revoke and create another). The list afterwards shows status only (pending, consumed, expired, revoked) and a pending invitation can be revoked (its own tap). The authority needs a machine endpoint (`with-secrets service --machine-port 8790`), because that address goes into the bundle.
2. **New machine.** `with-secrets pair` asks for the bundle at a **hidden prompt** (nothing is echoed). Unattended, supply it instead through **`WITH_SECRETS_PAIRING_FILE`** (a path to a file holding the bundle; a Docker secret is mounted at `/run/secrets/with-secrets-pairing`, which is read with no variable at all) or **`WITH_SECRETS_PAIRING`** (the bundle itself; the least safe, because a process environment is easy to read). A file beats the variable. The command removes both variables from its own process once read, and the host service never passes them to a program it starts.
3. **The protocol.** The first request carries only the invitation id and a fresh nonce, on a connection made with a throwaway identity, so nothing about this machine is shown yet. The authority answers with its public identity certificate, a nonce and an HMAC-SHA-256 proof that binds the invitation, its own fingerprint and both nonces, computed from a key derived from the code. The machine checks the certificate profile, that the TLS certificate it just saw is that identity's, and the proof, **before** it sends anything about itself. Only then does it open a fresh TLS 1.3/HTTP/2 connection pinned to that identity certificate and register: its identity certificate, fingerprint, host name, a proof of possession (a signature by its identity key) and a registration HMAC. The code is never sent; the authority stores only a protected derived key and wipes it when the invitation ends.
4. **What the machine prints.** Its fingerprint and host name and that it is **Pending**. It cannot ask for secrets or make grants.
5. **Administrator.** The machine appears under **Machines** as Pending with its fingerprint and host name. Compare them with what the machine printed, then **Approve** (its own tap). After that the host pins the authority's signing key by itself and runs.

Rules worth knowing: an invitation works once (concurrent claims have exactly one winner; a retry of the identical registration after a lost answer returns the same result); a wrong, expired, used or revoked invitation all get the same refusal; five wrong proofs withdraw an invitation, and thirty refused attempts in ten minutes make the route answer "too busy" to everyone for a while; pairing a machine again while it is Pending refreshes its record, but a Trusted, Disabled or Untrusted machine is never changed by pairing (and the invitation is not used up); at most 32 machines may wait for approval, 4 under one host name, 8 invitations may be open and 4 registrations run at once. Every creation, attempt, refusal, expiry, consumption and approval is in the durable audit with no code or proof.

### The WSL path: the authority holds the store

For a host service in WSL that uses the Windows authority: `WSL client -> WSL host service -> mutual TLS 1.3 / HTTP/2 -> Windows host service and authority`. The **authority holds the data store**: the approval page, the passkey tap and the decryption happen on the Windows side; the WSL host service shows no page, reads no store and holds no key. The values come back only on the authenticated connection as a signed, one-time delivery (never to the CLI, never in a log, never on the host's disk); the host builds the child's environment and starts the program. A failure, a disconnect, a lock or a withdrawal of trust before the delivery means nothing runs. The CLI prints the authority's page link, which you open on Windows. Saved approvals are off in remote mode; grants work.

Not built: LAN or remote deployment guidance and an administration interface beyond loopback (deferred); creating a grant from a remote host (`approve`); the real Windows-authority / WSL-host run is not completed yet (the Linux machine key store is an owner-only file, weaker than CNG; see `docs/operations.md` section 8).
## Known limits

- **The page shows the code, but only so much of it.** It shows the whole command line, the inline code, and the first 200 lines (at most 16 KB) of each script file, with a `...cut` notice when there is more. A long or obfuscated script can still be hard to judge, and an agent can write a script that prints `$DB_URL` in a form that is not redacted. Approve only code you have read and understood.
- **Interpreters are allowed in one strict form only.** Options are not parsed: anything else is refused with "put options inside the script file". Program names are matched without regard to case; an argument with leading or trailing whitespace is refused.
  - `sh`, `bash`, `zsh`, `dash`, `ksh`, `fish`, `python`, `py`, `python3`: `PROG script [args]` (the first argument does not start with `-`) or `PROG -c CODE [args]`. Not allowed: `-`, `-l`, `--login`, `-e`, `-m`, `-u`, `-W`, `-X`, `-I`, `--`, combined flags.
  - `node`, `perl`, `ruby`: `PROG script [args]` or `PROG -e CODE`. Not allowed: `--env-file`, `-C`, `--require`, `-M`, `-I`, `-E`, `--test`, `--`, combined flags.
  - `powershell`, `pwsh`: `-NoProfile` (required), `-NonInteractive`, `-NoLogo` and `-ExecutionPolicy` with one of Bypass, RemoteSigned, Unrestricted, AllSigned, Restricted, Default, Undefined (each at most once, any order), then exactly `-File path [args]` or `-Command CODE` (one code argument), written in full and in any case. The `-File` path may not contain `[`, `]` or a backtick, in the script name or its folder (PowerShell reads it as a wildcard): run from another folder. Not allowed: abbreviations (`-f`, `-c`), a bare positional, `-EncodedCommand` in any form (`-e`, `-ec`, `-enc`), padded flags, flags starting with an en dash, em dash, horizontal bar or minus sign, and code on standard input.
  - `cmd`: `cmd /d /c TAIL` (or `/k`, `/r`; `/d` is required) where every word of the tail has only letters, digits and `. _ : \ / -`, and the first word is a `.cmd` or `.bat` file written with its extension, or `echo`, `dir`, `type`, `ver`. The script path itself may contain spaces and brackets (the working folder is written in full), but a folder name with a quote or one of `% ^ & | < > !` is refused for cmd. Not allowed: `/c` without `/d`, `/s` and other switches, quotes, spaces in a word, `% ^ & | < > !`, a name without an extension (PATHEXT lookup).
  - An interpreter with nothing to run (`bash`, `python`, `cmd`, `pwsh` alone) is refused: it would read code from outside the approval. The script an interpreter names must exist and be at most 1 MB; the page, the fingerprint and the file lock all use that one operand.
  - Any other program has no analysis: the page shows its `Run:` line; a first file argument is only guessed and marked "guessed from the arguments, not verified"; a program that is itself a text script (`.cmd`, `.bat`, `.ps1`, `.sh`, `.py`, `.js`, `.pl`, `.rb`) is shown and hashed with its arguments unparsed.
- **Limits that remain.**
  - Where the system cannot lock a file (Linux, macOS, WSL), the program runs a private copy of each shown script. The copy's folder also holds a link for each entry of the original's folder (none when that folder has more than 1000 entries), so what a script finds by its own location (`dirname "$0"`, `BASH_SOURCE`, Python's `Path(__file__).resolve().parent` and `sys.path[0]`, `require('./x')`, `$PSScriptRoot`) is found as before. What is **not** the same: `$0`, `BASH_SOURCE`, `__file__` and `$PSScriptRoot` are the copy's path (the file name is the same); `..` from the script's folder is the private folder, not the original's parent; the copy's folder cannot be written, so a script that writes a new file beside itself fails (writing to a file that already exists beside it works, through its link); and what a script loads through those links is the neighbour as it is when used, not what was shown or approved (see the next item). On Windows the file itself runs, held against changes, and every path is the original's.
  - **What an approval covers.** The file or files shown (the script, and a program that is itself a text file), their hashes and the fingerprint: nothing else. Files a shown script loads (`source`, `import`, `require`, dot-sourcing, `-m` modules, `bash -c` code that runs other files) are not shown, hashed or held, on every system, and are read as they are when the script runs; a change to one after approval changes what runs and is not stopped. The approval page and the terminal text say so next to every script ("Approved: the file above only. Not approved: any file it loads or runs"). Code and data cannot be told apart reliably (a data file can be `eval`ed, a module can be a config), so no distinction is made and nothing is scanned for. To have code covered, put it in the script.
  - **What the private copy protects against, and what it does not.** It protects against the original changing or being replaced after approval, against another user of the machine (the folder is owner-only), and against a copy that was altered before the start (found: nothing runs). The copy is checked again in the step that starts the program, by its path; the interpreter then opens it by its path, a moment later. **A process of the same user can still change the copy in that moment** (it owns the folder and can loosen its permissions), and no call available without a native helper or a privilege ties the check to the open. This is not claimed to be prevented: such a process can already read the program's environment, and so the secrets, from `/proc` (tested on Linux with `ptrace_scope=1`), so the approval is not a defence against code the person already runs as themselves. The original is never run in place of the copy; a copy that cannot be made or checked stops the run.
  - Startup files can still load. The allowed forms refuse `-l` and other options, but zsh always reads `~/.zshenv`, fish reads its config, Python loads its user site (`.pth` files, `usercustomize`), and similar files exist for other runtimes. An agent that can write to your profile or startup files can use them to run code the page never showed.
  - A script given to an interpreter must be text: binary scripts, zipapps and `.pyc` files are refused. Windows PowerShell 5.1 (`powershell`, not `pwsh`) refuses a script with non-ASCII bytes and no UTF-8 BOM, because it would read it in another code page than the page shows. A program that resolves to a Windows App Execution Alias (a zero-length reparse point in a `WindowsApps` folder, such as the `python3` stub, `winget` or `wt`) is refused with a message that names it; use the full path to the real program. A `.cmd` or `.bat` file (as the script of `cmd`, or run directly) must be ASCII: cmd reads it in the console code page, so a byte above 127 could mean another character than the page shows. A batch file run directly is started as `cmd.exe /d /c "path" args`, so the AutoRun commands of the registry are skipped.
  - Other startup code is not covered: a console code page that is a double-byte one (DBCS) can read ASCII-looking bytes in a `.ps1` or other script differently, and anything a profile or the registry runs outside the forms above. A renamed or copied interpreter skips the analysis; the `Run:` line still shows the real path and is what to check.
  - The environment denylist (the variables listed above) cannot be complete. Known gaps (the list is not complete): `PSModulePath`, `COMSPEC`, the effect of `PATH` and `PATHEXT` on programs the child starts, other `GIT_*` variables, and other runtime-specific `*OPT`/`*OPTS` variables.
  - The write lock: on Windows the files the page showed are opened so that nobody can write or delete them until the program ends, and are hashed once more after that (if that fails the run is refused). It covers only those files, not a renamed parent folder or a junction. Off Windows there is no lock: the files are only checked just before launch and an interpreter may read a file again after it was changed.
- **`.env` declarations are written by the agent.** The environment denylist cannot be complete, so an ordinary `.env` value (such as `GIT_CONFIG_COUNT`, `HTTPS_PROXY`, `SSL_CERT_FILE`, `CORECLR_PROFILER_PATH`, `GH_HOST`, and now also `NODE_OPTIONS` or `PYTHONSTARTUP`) can reach the program; that is why the page shows every ordinary value and warns first about the ones that change which code runs. Anything the page cannot show (an encrypted value, a secret) is never given to such a name. Anyone with the public key in the `.env` can write an `encrypted:` value, so the page shows a fingerprint of each ciphertext and warns about a file that is not the project's own. A value is shown only if it is on the page: a program that reads the `.env` (or `.env.local`) itself sees the whole file. The inherited environment of the `with-secrets` process is not shown, and an agent controls it too.
- **Redaction does not catch** reversed, split, compressed, or encrypted copies.
- **A program that sends its environment over the network is out of scope.**
- **No length limit on the command** except a technical one of 16,000 characters. The program refuses a longer command instead of cutting it short.
- **Only file symbolic links are shown.** A link in a parent folder (a junction, for example) is not.
- **A script can load other files.** The page shows, hashes and locks only the files named in the command (the script an interpreter runs, and a program that is a text script). Files that script loads are not shown, hashed or locked.
- **Same OS user.** (See also the memory and look-alike page limits under "The secret store".) An agent that runs as you can write `state.db` in the store folder and read the process's memory at any moment a run is open (where the store key, the master key and the PRF output are for a moment); it cannot decrypt the secrets from the disk alone, because the store key is not on it. An edit to your passkeys, settings or secret rows fails verification and stops everything, and an edited or forged grant is ignored. But the agent can still delete `state.db` and write a whole new state signed by its own software key, with no page and no terminal; that key then approves its runs. The admin keys' fingerprints make that visible to you: they change on every page and in the audit history. The agent can also restore an older copy (accepted, see [Admin keys](#admin-keys)), or rewrite the audit log (and recompute the hash chain). The hook and file permissions must protect that folder, like the store itself.
- **Sign counts are not signed.** They sit outside the manifest signature. An agent can set the admin keys' counts very high, and then every admin assertion fails ("sign count did not increase"). This is denial of service only: deleting `state.db` does the same.
- **The first passkey is trust on first use.** Whoever finishes the first-time setup becomes the first admin. Do it yourself, in your own terminal.
- **An agent that owns your terminal** can read the link and the confirmation code. Use a terminal the agent cannot read.
- **Plain `http` is not accepted for passkeys** except on localhost. Use `https` for any other name.
- **`.cmd` and `.bat` programs** run through `cmd.exe`, which reads quotes and `& | < > ^ % !` in arguments as commands. Arguments that contain them are refused.
- **A store made before the shared PRF salt (commit a9dddd7) does not work.** Delete `state.db` and set up again.
- **Passkeys that are not discoverable can no longer sign.** Approval sign-in lists the passkeys for `localhost`; make new passkeys discoverable.
- **Output is read as UTF-8.** Binary output and output in another code page (the console's OEM page, UTF-16) are garbled, and UTF-16 copies of a secret are not redacted.
